# Автообновление

Документ описывает, как включить автообновление Torrenta, как обращаться с ключами
подписи и почему в проекте подписываются обновления, а не код.

Состояние на 1.8.0: плагин обновлений подключён (`tauri-plugin-updater` в
`src-tauri/Cargo.toml`, регистрация в `src-tauri/src/lib.rs`), но не настроен —
в `src-tauri/tauri.conf.json` нет публичного ключа и эндпоинта. Поэтому проверка
обновлений честно отвечает «обновления не настроены: нет ключа подписи», а не
делает вид, что всё хорошо. Ниже — шаги, чтобы это изменить.

## 1. Как работает механизм

1. Приложение (по команде пользователя или по расписанию) запрашивает JSON-манифест
   по одному из адресов `endpoints`.
2. В манифесте указана новая версия, ссылка на пакет обновления и его **подпись**.
3. Если версия больше текущей, приложение скачивает пакет и проверяет подпись
   публичным ключом из `pubkey`. Ключ зашит в приложение, подделать проверку нельзя.
4. Подпись совпала — запускается установщик (`passive` по умолчанию: прогресс без
   вопросов), приложение закрывается и после установки запускается снова.
5. Подпись не совпала или пакет повреждён — установка не выполняется.

Ответ `204 No Content` означает «обновлений нет» — это не ошибка.

## 2. Подпись обновления и подпись кода — разные вещи

Это самое частое место путаницы, поэтому явно:

| | Подпись кода (Authenticode) | Подпись обновления (minisign) |
| --- | --- | --- |
| Что подписывается | `.exe` и `.msi` установщика | пакет обновления (`.nsis.zip` / `.msi.zip`) |
| Кто выдаёт ключ | удостоверяющий центр (УЦ), платно | проект сам генерирует пару ключей, бесплатно |
| Что проверяет | Windows / SmartScreen | само приложение перед установкой |
| Защищает от | предупреждения «Неизвестный издатель» | подмены пакета, MITM, чужого обновления |
| Нужен ли сертификат | да, обязателен | нет |

**Подпись кода без сертификата невозможна.** Authenticode требует сертификат от
публичного УЦ (OV — примерно от 200 USD в год, EV — дороже и с аппаратным
токеном), а самоподписанный сертификат Windows доверенным не считает. Поэтому в
CI подписи кода нет: релизный установщик выходит неподписанным, и SmartScreen
один раз предупредит пользователя при первом ручном запуске установщика.

**Подпись обновления решает другую задачу и доступна бесплатно.** Пара ключей
minisign (Ed25519) генерируется один раз; приватным ключом подписывается каждый
пакет обновления, публичный ключ зашит в приложение. Благодаря этому:

* приложение не установит обновление, подписанное чужим ключом;
* перехваченный или испорченный при скачивании пакет не установится;
* не нужен ни сертификат, ни УЦ, ни деньги.

Подпись обновления **не заменяет** Authenticode: если Windows показывала
предупреждение при запуске установщика, она его покажет и для обновления. Это
осознанный компромисс: безопасность доставки обновления обеспечивается, а
репутация издателя в SmartScreen — вопрос сертификата.

## 3. Что уже есть в проекте

* Плагин `tauri-plugin-updater` в зависимостях `src-tauri/Cargo.toml` и
  зарегистрирован в `src-tauri/src/lib.rs`.
* Раздел `plugins.updater` в `src-tauri/tauri.conf.json` — пока пустой:
  `"active": false`, `"endpoints": []`, `"pubkey": ""`.
* Команда `check_update`, которую использует окно «Диагностика».

Замечание про `"active": false`. В Tauri 2 у плагина обновлений нет поля `active`
(оно было в Tauri 1 и осталось только в разделе `bundle`). Поле в конфиге
оставлено как понятная человеку пометка «выключено», плагин его не читает.
Фактически обновления выключены потому, что пусты `endpoints` и `pubkey`: без
адреса проверять нечего, без ключа нечем проверять подпись.

## 4. Шаг 1. Сгенерировать пару ключей

В репозитории есть скрипт-обёртка над штатным генератором Tauri:

```powershell
.\scripts\gen-updater-key.ps1
```

Скрипт вызывает `tauri signer generate`, создаёт пару в `.tauri-keys\` (файл
приватного ключа `torrenta.key` и `torrenta.key.pub`), печатает **публичный**
ключ и готовый фрагмент конфигурации. Приватный ключ и пароль в вывод не
попадают — их нельзя копировать в чаты, задачи и логи CI.

Параметры:

| Параметр | Смысл |
| --- | --- |
| `-Password <строка>` | пароль на приватный ключ; без параметра скрипт спросит скрыто (пустой ввод — ключ без пароля) |
| `-KeyPath <путь>` | куда положить ключ; по умолчанию `.tauri-keys\torrenta.key` |
| `-Force` | перезаписать существующий ключ; **старым ключом подписаны прошлые обновления**, менять ключ можно только вместе с публикацией новой версии со сменой `pubkey` |
| `-Help` | справка |

Требования и правила работы с ключом:

* `.tauri-keys/` уже в `.gitignore` — приватный ключ не должен попасть в репозиторий.
  Скрипт сам проверяет это и предупреждает, если строка из `.gitignore` исчезла.
* Пароль на ключ рекомендуется: утечка незашифрованного ключа равносильна передаче
  прав на выпуск обновлений всем желающим.
* **Сделайте резервную копию ключа и пароля в защищённом месте.** Потеря ключа =
  невозможность обновить уже установленные копии: у них зашит старый `pubkey`,
  и обновление новым ключом они не примут. Тогда остаётся только ручная
  переустановка у пользователей.

## 5. Шаг 2. Прописать ключ и эндпоинт

`src-tauri/tauri.conf.json`, раздел `plugins`:

```json
{
  "plugins": {
    "updater": {
      "active": true,
      "endpoints": [
        "https://<ваш-сервер>/torrenta/{{target}}/{{arch}}/{{current_version}}"
      ],
      "pubkey": "<содержимое torrenta.key.pub одной строкой>"
    }
  }
}
```

Поддерживаемые поля плагина (Tauri 2, camelCase):

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `pubkey` | да | публичный ключ minisign одной строкой |
| `endpoints` | да | список URL манифеста; проверяются по порядку, пока один не ответит |
| `windows.installMode` | нет | `passive` (по умолчанию, прогресс без вопросов), `basicUi` (обычный мастер установки), `quiet` (полностью без интерфейса, при установке от администратора) |
| `dangerousInsecureTransportProtocol` | нет | разрешить `http` вместо `https`; только для локальной отладки — в релизной сборке плагин иначе отвергает не-https эндпоинт |
| `requireSignedVersion` | нет | требовать, чтобы подпись содержала версию, и сверять её с манифестом — защита от отката на старую подпись |
| `allowDowngrades` | нет | разрешить установку версии не новее текущей (по умолчанию запрещено) |

Плейсхолдеры в `endpoints`: `{{current_version}}`, `{{target}}`, `{{arch}}`,
`{{bundle_type}}`. На Windows x64 `{{target}}` = `windows`, `{{arch}}` = `x86_64`,
`{{bundle_type}}` = `nsis` или `msi`.

## 6. Шаг 3. Включить артефакты обновления

Установщик сам по себе не является пакетом обновления: Tauri собирает для
обновления отдельный архив и `.sig` к нему. Включается в `src-tauri/tauri.conf.json`:

```json
{
  "bundle": {
    "createUpdaterArtifacts": true
  }
}
```

После включения рядом с установщиками появятся файлы обновления и подписи
(`*.nsis.zip`, `*.nsis.zip.sig`, `*.msi.zip`, `*.msi.zip.sig`). Значение
`"v1Compatible"` создаёт дополнительно совместимые с Tauri 1 архивы — нужно только
при обновлении старых установок, которые живут на старом механизме.

Без заданного приватного ключа сборка с включённым `createUpdaterArtifacts`
завершается ошибкой: подписать пакет нечем. Это защита от выпуска обновления,
которое никто не сможет установить.

## 7. Шаг 4. Собрать и подписать

Переменные окружения (их читает сам Tauri CLI):

| Переменная | Где | Смысл |
| --- | --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | CI и локально | приватный ключ: содержимое файла строкой |
| `TAURI_SIGNING_PRIVATE_KEY_PATH` | локально | путь к файлу ключа — альтернатива предыдущей переменной |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | CI и локально | пароль ключа, если ключ создан с паролем |

Локально удобнее путь:

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY_PATH = (Resolve-Path '.tauri-keys\torrenta.key').Path
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = '<пароль>'
.\build-windows.ps1
```

Для сборки через `tauri build` действует то же: переменные должны быть в
окружении процесса, а не только в профиле PowerShell.

## 8. Шаг 5. Выложить обновление на сервер

Достаточно обычного статического хостинга: манифест с версией и ссылками плюс
сами файлы `.zip` и `.sig`. Два варианта эндпоинта.

**Статический манифест (проще).** Один JSON на релиз, платформы перечислены
внутри; приложение само выбирает нужную запись. Эндпоинт вида
`https://<ваш-сервер>/torrenta/latest.json`:

```json
{
  "version": "1.7.1",
  "notes": "Исправлена сортировка по размеру",
  "pub_date": "2026-02-01T12:00:00Z",
  "platforms": {
    "windows-x86_64-nsis": {
      "signature": "<содержимое torrenta_1.7.1_x64-setup.nsis.zip.sig>",
      "url": "https://<ваш-сервер>/torrenta/torrenta_1.7.1_x64-setup.nsis.zip"
    },
    "windows-x86_64-msi": {
      "signature": "<содержимое torrenta_1.7.1_x64_en-US.msi.zip.sig>",
      "url": "https://<ваш-сервер>/torrenta/torrenta_1.7.1_x64_en-US.msi.zip"
    }
  }
}
```

Ключи платформы: `{os}-{arch}-{bundle_type}`, затем `{os}-{arch}` как запасной.
Если в сборке только NSIS, достаточно `windows-x86_64-nsis` и `windows-x86_64`.

**Динамический эндпоинт (сервер решает сам).** Адрес содержит
`{{current_version}}`, `{{target}}`, `{{arch}}`, сервер отвечает одним объектом
`{"version": "...", "url": "...", "signature": "..."}` или `204`, если обновления
нет. Такой вариант удобен, если хочется отдавать разные каналы (stable/beta) в
зависимости от версии.

Правила:

* `signature` — **всё содержимое** файла `.sig` одной строкой, а не путь и не хэш.
* `url` должен быть доступен без авторизации и по `https`.
* `version` должна быть строго больше текущей версии приложения (semver), иначе
  обновление не предложится.
* Манифест и файлы лучше держать на одном хосте: меньше поводов для расхождений.

## 9. Шаг 6. Приватный ключ в CI

Приватный ключ живёт только в секретах GitHub, в репозиторий не попадает:

* **Settings → Secrets and variables → Actions → New repository secret**;
* имя `TAURI_SIGNING_PRIVATE_KEY` — значение целиком из файла `torrenta.key`
  (многострочный текст, включая строки `untrusted comment:` и
  `trusted comment:`);
* при ключе с паролем — второй секрет `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.

Локальный путь `.tauri-keys/torrenta.key` в CI не работает: там нет вашего
диска, поэтому в секрет кладётся содержимое, а не путь.

Сейчас `.github/workflows/build.yml` обновления не подписывает: задача CI —
проверки и релизный бинарник, установщики собираются локально через
`build-windows.ps1` (см. `docs/BUILD.md`). Чтобы подписывать в CI, к шагу сборки
добавляются переменные окружения:

```yaml
      - name: Релизная сборка с подписью обновления
        env:
          TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
          TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}
        run: npm run tauri build
```

Правила безопасности для CI:

* не печатать ключ и пароль в лог, не передавать их аргументом командной строки
  (видны в списке процессов);
* не добавлять ключ в артефакты и кэш;
* для сборок из форков ключ не выдавать вообще: PR из форка не должен уметь
  подписывать релиз.

## 10. Как проверить, что обновление работает

1. Соберите версию, поднимите локальный сервер с манифестом и пакетом
   (для локальной отладки `http://localhost` требует
   `dangerousInsecureTransportProtocol: true`).
2. Установите собранное приложение версии `N`, в манифесте укажите `N+1`.
3. Откройте «Диагностику» — состояние обновлений должно смениться с «не настроены»
   на «доступна версия N+1».
4. Запустите обновление, убедитесь, что приложение закрылось, установилось и
   открылось уже с новой версией.
5. Негативные проверки обязательны: подмените один байт в пакете (подпись не
   совпадёт — установка должна быть отклонена), укажите в манифесте версию
   `N-1` (обновление не предлагается), уберите запись платформы из `platforms`
   (должна быть ошибка «платформа не найдена», а не тихий отказ).

## 11. Частые ошибки

| Симптом | Причина |
| --- | --- |
| «обновления не настроены: нет ключа подписи» | пустой `pubkey` в `tauri.conf.json` |
| «Updater does not have any endpoints set» | пустой `endpoints` |
| ошибка TLS / `InsecureTransportProtocol` | эндпоинт по `http` в релизной сборке |
| «подпись не совпала» после обновления ключа | у установленных копий зашит старый `pubkey` — нужен релиз со сменой ключа |
| «платформа не найдена» (`TargetNotFound`) | в `platforms` нет `windows-x86_64` или `windows-x86_64-nsis` |
| обновление не предлагается | версия в манифесте не больше текущей |
| сборка падает на этапе бандла | включён `createUpdaterArtifacts`, но ключ не задан |

## 12. Ограничения

* Откат версии автоматически не поддерживается: обновление только «вперёд»
  (`allowDowngrades` по умолчанию выключен и включать его не рекомендуется).
* Установка выполняется установщиком и требует прав, соответствующих режиму
  установки; при `currentUser` права администратора не нужны.
* Автообновление не отменяет ручную проверку: пользователь всегда может
  переустановить приложение из установщика, скачанного с сайта.
