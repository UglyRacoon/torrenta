# Torrenta 1.7.0 — что добавлено

Версия 1.7.0 закрывает P3 из плана развития: расписание лимитов, последовательная
загрузка, редактирование трекеров, окно диагностики и портативный режим. Но
главная её причина — баг-репорт пользователя: двойной клик по `.torrent`-файлу
поднимал приложение без окна добавления, а при нескольких попытках открывалось
несколько экземпляров программы. Разбор закончился собственным модулем работы с
ассоциацией файлов, который умеет проверять и лечить привязку.

Здесь описано, как всё устроено на самом деле: что проверено тестами, что
проверено руками, и что до сих пор не работает или работает с оговорками.

---

## 1. Требования пользователя

1. **Расписание лимитов.** В заданном окне времени действуют отдельные лимиты
   скорости — чтобы ночная раздача не забивала канал.
2. **Последовательная загрузка.** Возможность качать торрент по порядку кусков, а
   не «где быстрее».
3. **Трекеры в интерфейсе.** Посмотреть список трекеров торрента, отредактировать
   его и принудительно объявиться.
4. **Окно диагностики.** Одно место, где видно реальное состояние движка: DHT,
   пиры, проброс порта, расписание, действующие лимиты.
5. **Портативный режим.** Запуск с флешки с данными рядом с `torrenta.exe`.
6. **Заготовка автообновления.** Проверка обновлений, выключенная по умолчанию,
   пока у проекта нет ключа подписи и адреса фида.
7. **Ассоциация `.torrent`-файлов.** Двойной клик по торрент-файлу должен
   открывать один экземпляр Torrenta с окном добавления и этим файлом.

Требование 7 появилось не из плана, а из репорта после 1.6.0: пользователь
описал именно такое поведение. Поэтому у него есть отдельный раздел (§9), а не
строчка в списке.

## 2. Последовательная загрузка

**Что делает.** Торрент скачивается кусками по возрастанию индекса: сначала
начало файла, потом следующее. Удобно для видео и больших образов, когда хочется
начать пользоваться файлом, не дожидаясь конца загрузки.

**Как устроено.**

* `crates/torrent-core/src/picker.rs` — `PiecePicker` получил режим
  `pick_order::PickOrder::{Rarest, Sequential}`. По умолчанию остаётся `Rarest`:
  в режиме `Sequential` метод `best()` сразу отдаёт `first_available()` —
  наименьший индекс среди нужных, отсутствующих и доступных у пира кусков.
  Уровни приоритетов файлов в этом режиме не действуют: последовательность важнее
  «важности» куска. Тесты: `sequential_order_takes_smallest_index`,
  `sequential_order_skips_missing_and_excluded`,
  `sequential_order_ignores_piece_levels`, плюс проверка переключения режима.
* `TorrentHandle` хранит флаг в атомике, `TorrentSnapshot.sequential` отдаёт его в
  интерфейс. Переключение на лету — `TorrentManager::set_sequential(id, on)`, оно
  не пересоздаёт торрент и не сбрасывает прогресс.
* `EngineConfig.sequential` применяется к **новым** торрентам; у уже добавленных
  режим остаётся тем, что выбрал пользователь. Команда
  `set_torrent_sequential`, переключатель — в карточке торрента.

**Ограничения (честно).**

* Это порядок кусков, а не потоковое воспроизведение: плеер не подключается,
  MIME-раздача не поднимается, и «смотреть сразу» получится только у форматов,
  которые умеют читать недокачанный файл.
* Уже скачанные куски не переупорядочиваются, режим влияет только на выбор
  следующих.
* Если нужный по порядку кусок есть не у всех пиров, скорость может просесть —
  режим не ищет компромисс, он строго идёт по индексам.
* Приоритеты файлов в этом режиме игнорируются (это следствие, а не баг), но
  исключённые из загрузки файлы по-прежнему не качаются.

## 3. Трекеры: просмотр, правка, повторный announce

**Что делает.** В карточке торрента появился блок «Трекеры»: список адресов,
редактирование, кнопка «Обновить трекеры». Изменения применяются без
перезапуска торрента.

**Как устроено** (`crates/torrent-core/src/engine/mod.rs`).

* `trackers(id) -> Result<Vec<String>, EngineError>` — текущий список.
* `set_trackers(id, urls)` — нормализация и замена списка. Правила
  `normalize_trackers`:
  * пробелы по краям обрезаются, пустые строки пропускаются;
  * адрес разбирается `url::Url`; ошибка — `InvalidInput("некорректный адрес
    трекера: …")`;
  * разрешены только схемы `http`, `https`, `udp`; иначе
    `InvalidInput("неподдерживаемая схема трекера: …")`;
  * нужен хост, иначе `InvalidInput("в адресе трекера нет хоста: …")`;
  * дубликаты отбрасываются без учёта регистра;
  * больше `MAX_TRACKERS = 100` адресов не сохраняется (лишние молча
    отбрасываются);
  * пустой список допустим — тогда пиры ищутся только через DHT и PEX.
  После записи вызывается `refresh_trackers()`, чтобы анонсер увидел новый список.
* `reannounce(id)` — если трекеров нет, возвращает
  `InvalidInput("нет трекеров")`; иначе будит анонсер (`wake_announcer()`).
* Команды: `torrent_trackers`, `set_torrent_trackers`, `reannounce_torrent`.
  Ошибки возвращаются строкой и показываются в карточке.

**Ограничения (честно).**

* «Обновить трекеры» не делает синхронный HTTP-запрос: оно поднимает анонсер, и
  фактический announce происходит на ближайшей итерации цикла. Поэтому кнопка
  не «ждёт ответа трекера» и не показывает его результат.
* Обрезка до 100 адресов не сообщается пользователю отдельным предупреждением.
* Удаление трекера не отменяет уже полученных пиров — они живут до разрыва
  соединения; DHT-обнаружение при этом продолжает работать.

## 4. Расписание лимитов

**Что делает.** В настройках можно включить окно времени и задать отдельные
лимиты загрузки/отдачи внутри него. Вне окна действуют базовые лимиты.

**Как устроено.**

* `EngineConfig` получил поля `schedule_enabled`, `schedule_from_min`,
  `schedule_to_min`, `schedule_download_limit_kib`, `schedule_upload_limit_kib`
  (минуты от полуночи, КиБ/с).
* `sanitized()`: минуты берутся по модулю 1440, лимиты ограничены
  `MAX_SCHEDULE_LIMIT_KIB` (1 048 576 КиБ/с), окно нулевой длины
  (`from == to`) выключает расписание целиком — иначе получилось бы «никогда» или
  «всегда» вместо понятного поведения.
* Окно через полночь поддерживается: при `from > to` активность считается как
  `from <= minute || minute < to`; начало включительно, конец — нет.
* `update_schedule_limits()` пересчитывает действующие лимиты на каждом тике
  статистики (`STATS_TICK` = 500 мс) и сразу после смены настроек, затем очередь
  закачек пересобирается (`schedule()`), чтобы лимиты применились к активным
  торрентам.
* `TorrentSnapshot` отдаёт действующие лимиты, то есть в окне расписания в
  интерфейсе видны значения расписания, а не базовые.

**Ограничения (честно).**

* Локальное время берётся только в Windows (`GetLocalTime` через FFI на
  `SYSTEMTIME`, без новых зависимостей). На других платформах используется UTC —
  для тестов это нормально, для реального пользователя не-Windows версии
  расписание будет смещено. Windows — единственная целевая платформа релиза.
* Расписание меняет лимиты, но не ставит торренты на паузу: «полностью
  отключить ночью» можно, задав лимиты 0, а не отдельным переключателем.
* Границы окна не привязаны к дням недели, праздникам и часовому поясу.
* Лимит применяется к движку целиком; per-torrent лимиты расписанием не
  затрагиваются.

## 5. Диагностика

**Что делает.** Отдельное окно (боковая панель → «Диагностика», горячая клавиша
Ctrl+D, в русской раскладке — Ctrl+В) показывает состояние движка одной страницей
и обновляется каждые 2 секунды.

**Как устроено.**

* Ядро: `pub struct Diagnostics` (22 поля) и `TorrentManager::diagnostics()`.
  Поля: `listen_port`, `dht`, `dht_port`, `dht_nodes`, `pex`, `web_seeds`,
  `proxy`, `port_mapping`, `mapped_external`, `schedule_enabled`,
  `schedule_from_min`, `schedule_to_min`, `schedule_active`,
  `download_limit_kib`, `upload_limit_kib`, `sequential`, `torrents`, `active`,
  `peers`, `download_bps`, `upload_bps`, `uptime_secs`.
* `src-tauri/src/commands.rs` — команда `engine_diagnostics` и DTO
  `DiagnosticsDto`; снимок собирается в `spawn_blocking`, чтобы замки движка не
  блокировали поток интерфейса.
* `src/ui/diagnostics.ts` — самодостаточное окно: открытие, закрытие по Escape,
  ловушка фокуса, обновление по таймеру, кнопка «Обновить»; данные разбиты на
  группы «Сеть», «Расписание и лимиты», «Торренты и пиры», «Обновления» и
  «Данные». Пока окно открыто, таймер живёт; при закрытии очищается.
* Горячая клавиша не перебивает открытый диалог и не срабатывает при вводе
  текста (`isEditableTarget`).

**Ограничения (честно).**

* Окно только читает состояние: из него нельзя включить DHT или поменять порт.
* `mapped_external` берётся через `try_lock` на структуре проброса: если в этот
  момент идёт обновление, поле покажет «нет данных» вместо ожидания. Это
  осознанный выбор в пользу отзывчивости интерфейса.
* Если движок недоступен, окно показывает сообщение, а не пустые нули.
* `dht_port` — настроенное значение, а не фактически занятый порт: UDP-сокет DHT
  может занять другой порт, если указанный занят.
* Экспорта диагностики в файл и копирования отчёта одной кнопкой нет.
* `uptime_secs` считает время жизни менеджера: перезапуск движка (например, после
  смены настроек) обнуляет счётчик.

## 6. Список торрентов: поиск и мультисортировка

**Что делает.** В списке появился поиск и сортировка по нескольким полям сразу
(до трёх), которая запоминается между запусками.

**Как устроено.**

* `src/ui/list.ts`: `MAX_SORT_KEYS = 3`, `SortSpec { key, dir }`, ключ
  `localStorage["torrenta.sort"]`. При чтении значение нормализуется: мусор и
  неизвестные поля отбрасываются, повторы схлопываются, число ключей
  ограничивается.
* Направление по умолчанию зависит от поля: `added`, `size`, `progress`,
  `speed`, `ratio` — по убыванию; `name` и `state` — по возрастанию. Это
  соответствует тому, что человек ожидает увидеть: новые сверху, файлы от
  больших к меньшим, алфавит — от «А».
* Поиск — `role="searchbox"` с очисткой; сортировка — панель `role="dialog"`,
  где можно добавить поле, сменить направление и убрать его.
* Сравнение идёт по уже полученным снимкам состояния, то есть сортировка не
  трогает движок и работает мгновенно.

**Ограничения (честно).**

* Сортировка и поиск клиентские: на движок и на очередь закачек они не влияют.
* Поиск — подстрока без учёта регистра, без нечёткого совпадения и без поиска по
  хешу или трекерам.
* Значения хранятся в `localStorage`, поэтому сброс профиля браузера (или
  `%APPDATA%`) сбрасывает настройку сортировки.

## 7. Портативный режим

**Что делает.** Если рядом с `torrenta.exe` лежит файл-маркер, все данные
приложения (настройки, сессия) складываются в подкаталог рядом с программой, а не
в профиль пользователя. Каталог можно целиком перенести на флешку.

**Как устроено** (`src-tauri/src/settings.rs`).

* Маркеры: `torrenta-portable.txt` или `portable` в каталоге исполняемого файла.
* Данные: `<каталог exe>\TorrentaData`.
* `resolve_data_dir(exe_dir, app_dir)` выбирает портативный каталог только при
  наличии маркера и после проверки записи: `ensure_writable_dir()` создаёт
  каталог и пишет пробный файл `.torrenta-write-test`. Если прав нет — причина
  уходит в stderr, приложение продолжает работать на обычном каталоге
  конфигурации с `portable: false`. Запуск важнее портативности.
* `portable_info` отдаёт в интерфейс фактический путь и флаг — чтобы не
  догадываться, какой каталог используется.

**Ограничения (честно).**

* Режим не шифрует данные и не изолирует их от системы: это просто другой путь.
* Обновление приложения при этом всё равно ставится в обычное место установки —
  портативность касается данных, а не установщика.
* Проверка записи идёт один раз при старте: если каталог станет недоступен
  позже, ошибки будут уже при сохранении.

## 8. Автообновление: заготовка, а не готовое обновление

**Что делает.** Команда `check_update` и окно диагностики умеют показать
состояние обновлений: настроено ли, какая версия стоит, есть ли новая.

**Как устроено.**

* Плагин `tauri-plugin-updater` подключён, `check_update` вызывает
  `app.package_info().version` и `updater().check()`.
* Если ключ подписи не задан (`plugins.updater.pubkey` пустой), возвращается
  `configured: false` с пояснением «обновления не настроены: нет ключа подписи».
  Это не ошибка сети, а честное состояние: без ключа обновление не проверить и не
  подписать.
* Если ключ задан, но адреса фида нет, команда возвращает `configured: true` и
  сообщение о неполной настройке, а не падает.

**Ограничения (честно).**

* Реального фида обновлений у проекта пока нет: `plugins.updater.active` в
  `tauri.conf.json` выключен, ключей подписи в релизе нет. Значит, автопроверка
  в поставке не работает — функция готова, но не включена.
* Скачивания и установки обновления из интерфейса нет: только проверка.
* Самообновление требует подписи артефактов; без ключа обновлять нечего и
  небезопасно.

## 9. Ассоциация файлов `.torrent` и самолечение

**Зачем.** Пользователь сообщил: «при клике на торрент-файл открывается
приложение, но окно добавления торрента не показывает; если несколько раз
попытаться открыть торрент-файл двойным кликом, откроется столько же экземпляров
программы». Разбор на живой машине показал две причины, обе — в реестре
пользователя, а не в коде 1.6.0:

1. `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\FileExts\.torrent\UserChoiceLatest\ProgId`
   указывал на `Applications\torrenta.exe`, и команда запуска вела на **старый
   exe версии 1.3.1**. В той сборке не было ни пересылки аргумента, ни
   single-instance, ни окна добавления: каждый клик стартовал новый экземпляр без
   диалога.
2. Второй вариант: `UserChoiceLatest` с **пустым** `ProgId` при живом `Hash`. В
   таком состоянии Windows не открывает вообще ничего.

Лечение «руками» (удалить `UserChoiceLatest`, `OpenWithList`, `OpenWithProgids`
для `.torrent`) восстановило разрешение, а установка 1.6.0 поверх старого каталога
`%LOCALAPPDATA%\Torrenta` (то есть поверх 1.3.1) закрыла проблему навсегда.
Пользователь это подтвердил. Но лечить это каждый раз руками — неправильно,
поэтому в 1.7.0 появился модуль `src-tauri/src/association.rs`.

**Как устроено.**

* Порядок слоёв ассоциации, который реально действует в Windows:
  `UserChoiceLatest\ProgId` (самый новый, побеждает) → `UserChoice\ProgId` →
  `HKCU\Software\Classes\.torrent` → HKLM. `assoc`/`ftype` читают только HKLM,
  поэтому ими нельзя проверить фактическую привязку; `AssocQueryString` на этой
  машине вернула ошибку и непригодна.
* Чтение отдаёт `HandlerView { progid, command, source }`, где `source` —
  `HandlerSource::{Missing, Classes, UserChoiceLatest, UserChoice, EmptyChoice}`.
* Решение принимает чистая функция `decide()` → `Decision::{Keep, Claim,
  RepairStalePath}`; она отвязана от реестра и покрыта 27 тестами без Windows.
* Запись при `Claim`/`RepairStalePath`: ProgId `Torrenta.torrent`, `Torrenta.magnet`,
  `Applications\torrenta.exe` с командой `"<путь к exe>" "%1"` (кавычки вокруг
  exe и `%1` — иначе пути с пробелами ломаются; `reg.exe` в этом месте портит
  кавычки, поэтому пишем через Win32 `RegSetValueExW`).
* Нельзя перехватывать живой чужой обработчик: если `.torrent` открывается
  qBittorrent и его exe существует, решение — `Keep`, `is_owner = false`.
* Нельзя оставлять битый `UserChoice`: пустой `ProgId` или мёртвый путь
  (файла нет) — такой ключ удаляется, а не перезаписывается нашими значениями.
  `Hash` мы не подделываем: Windows сама сбрасывает невалидный `UserChoice`.
* API: `ensure()` (при старте, если `associate_files` включён), `status()` (только
  чтение), `repair()` (кнопка в настройках). Результат кладётся в
  `AssociationSlot` (обычный `Mutex<AssociationState>`), откуда его читают
  команды `association_status` и `repair_association`.
* Интерфейс: блок «Ассоциация файлов» в настройках — переключатель «Связывать
  файлы .torrent с Torrenta», строка статуса с тонами (ok / warn / error /
  muted), кнопка «Починить ассоциацию» с состояниями «Проверяем…»,
  «Ассоциация восстановлена», «Torrenta уже открывает файлы .torrent». При
  выключенном переключателе кнопка заблокирована и объясняет, почему.
* Портативный режим учитывается: путь к exe берётся у текущего процесса
  (`AppEngine::exe_path()` без кэширования), поэтому копия программы регистрирует
  саму себя.

**Ограничения (честно).**

* Работает только в Windows. На других ОС `AssociationDto.available = false`,
  `repair_association` возвращает понятное сообщение, а не делает вид, что
  починил.
* Мы не пишем `UserChoice`/`UserChoiceLatest` и не подделываем `Hash` — политика
  такова, что «тихая» смена выбора пользователя не делается. Если Windows
  показывает диалог выбора приложения, его нужно пройти один раз.
* Живой чужой обработчик не перехватывается. Если `.torrent` открывается другой
  программой, пользователю придётся пойти в «Параметры → Приложения →
  Приложения по умолчанию»; кнопка «Починить» покажет `is_owner = false` и
  подсказку, но не отберёт привязку.
* `magnet` регистрируется только как ProgId, а не как URL-протокол: полноценное
  открытие `magnet:`-ссылок из браузера этой версией не обещается.
* Автотесты проверяют чистую логику принятия решений (27 тестов) и DTO (2 теста);
  сама запись в реестр на живой машине проверялась вручную, потому что на момент
  разработки машина была уже вылечена и повторять поломку в тесте нельзя.
* Если `UserChoiceLatest` содержит пустой `ProgId`, а `UserChoice` — живой чужой
  обработчик, приоритет разрешения остаётся за чужим слоем; `repair_association`
  запишет наши ключи, но фактическим обработчиком останется чужой, и
  `is_owner` будет `false`. Однокликнового «отобрать» нет — это осознанно.

## 10. Настройки версии 1.7

`SettingsDto` получил поля (все сохраняются в `settings.json`):

| Поле | Тип | По умолчанию | Смысл |
| --- | --- | --- | --- |
| `sequential` | `bool` | `false` | Новые торренты качаются последовательно |
| `schedule_enabled` | `bool` | `false` | Расписание лимитов включено |
| `schedule_from_min` | `u32` | `0` | Начало окна, минуты от полуночи |

| `schedule_upload_limit_kib` | `u32` | `0` | Лимит отдачи внутри окна, КиБ/с |

Все семь полей входят в хеш настроек, поэтому изменение любого из них

на движок, и при включении привязка регистрируется сразу, синхронно.

Старые `settings.json` без новых полей читаются нормально: недостающее
дополняется значениями по умолчанию.

## 13. Что осталось за рамками версии

* **Живой фид обновлений и подпись.** Ключ и endpoint не настроены;
  `check_update` возвращает `configured: false`.
* **Открытие `magnet:`-ссылок из браузера.** ProgId есть, протокол не
  зарегистрирован.
* **Полный перехват привязки.** Живой чужой обработчик не отбирается — только
  подсказка пользователю.
* **UDP-порт DHT.** Настраивается, но при занятости ОС может выбрать другой;
  фактический порт в диагностику не выводится.
* **Продление аренды проброса порта.** Проброс выполняется, автоматического
  продления lease по таймеру нет.
* **uTP.** Не реализован; используется TCP.
* **Потоковое воспроизведение.** Последовательная загрузка — не стриминг (см. §2).
* **Поиск по нескольким полям сразу.** Поиск один, по имени; сортировка — до трёх
  ключей.
* **Экспорт диагностики.** Нет копирования отчёта и логов из окна.
