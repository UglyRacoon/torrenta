# Torrenta 1.8.1 — сохранение прогресса и подменю скорости

Локальная сборка для проверки. На GitHub пока не выкладывается.

Две жалобы, обе воспроизводимые и обе — регрессии:

1. После перезапуска (в том числе аварийного) торрент начинал качать заново:
   и полностью скачанный, и скачанный наполовину.
2. Подменю «Ограничить скорость» в контекстном меню исчезало, как только
   курсор доходил до пункта со скоростью.

Ниже — причины и что изменено. Плюс сделан оптимистичный разчок: он был первым
пунктом плана после 1.8.0, и без него новые сиды вне топ-8 не получали от нас
данные (значит, и не разчокивали нас).

---

## 1. Почему прогресс терялся

`session.json` хранил только «что вернуть»: info-hash, источник, каталог,
выбранные файлы, паузу, лимиты, приоритеты. **Прогресса в нём не было вообще.**

Движок после `add_file_with` начинает как обычную новую загрузку: его битовая
карта кусков пустая, и он запрашивает у пиров всё подряд. Файлы на диске при
этом никто не проверял — хэширование запускалось только по кнопке
«Перепроверить файлы». Отсюда оба сценария из жалобы: готовый торрент после
старта снова качал все куски, а недокачанный начинал с нуля.

Дополнительно: сессия писалась только при изменении состава списка (сравнение
по хешу), поэтому при аварийном завершении могло потеряться и последнее
изменение состава.

## 2. Что сделано: быстрое возобновление

### 2.1 В ядре — карта кусков

Добавлен публичный тип и две ручки (`crates/torrent-core/src/engine/mod.rs`):

```rust
pub struct ResumeData {
    pub piece_count: u32,
    pub piece_length: u32,
    /// Битовая карта проверенных кусков, старший бит — кусок 0.
    pub pieces: Vec<u8>,
}

impl TorrentManager {
    pub fn resume_data(&self, id: u64) -> Result<ResumeData, EngineError>;
    pub fn apply_resume(&self, id: u64, data: &ResumeData) -> Result<(), EngineError>;
}
```

`apply_resume` не читает диск: она заменяет карту кусков, пересчитывает
`pieces_have`/`have_bytes`, выбрасывает недоделанные буферы и выставляет
состояние — `Seeding`, если всё на месте, иначе `Downloading`. Пауза
пользователя при этом сохраняется. Хэши не считаются, потому что решение
«доверять карте» принимает вызывающая сторона.

### 2.2 В сессии — карта и отпечатки файлов

`SessionEntry` получил поле `resume: Option<SessionResume>`:

```jsonc
"resume": {
  "pieces": "ff00c0",        // карта кусков в hex
  "piece_count": 812,
  "piece_length": 4194304,
  "files": [
    { "path": "D:\\Загрузки\\Фильм.mkv", "length": 7340032000, "mtime": 1794570000 }
  ],
  "saved_at": 1794570100
}
```

Отпечатки (размер + mtime каждого файла) — это и есть проверка «файлы не
менялись». Без них доверять карте опасно: пользователь мог дописать файл,
переместить его или заменить.

Поле необязательное (`#[serde(default)]`), поэтому `session.json` от 1.8.0 и
раньше читается без ошибок — просто без карты.

### 2.3 Что происходит при старте

| Случай | Поведение |
| --- | --- |
| Карта есть, все файлы совпали по размеру и mtime | `apply_resume` — торрент сразу в `Seeding`/`Downloading` с реальным прогрессом, хэши не считаются |
| Карты нет (старый `session.json`, первый запуск после обновления) | `recheck` — полная проверка хэшами вместо повторной загрузки |
| Файлы изменились или пропали | `recheck` — карте не доверяем |
| Magnet-торрент | Карту применить нельзя, пока нет метаданных: она откладывается и применяется (или запускается `recheck`) на первом событии движка после получения метаданных |

Порядок важен: перед применением карты торрент принудительно ставится на паузу,
иначе движок успевает начать качать заново, пока мы сверяем отпечатки. После
применения пауза снимается, если торрент не был на паузе у пользователя.

### 2.4 Аварийное завершение

* Сессия пишется раз в 5 секунд при изменении полезной нагрузки (карта кусков
  меняется по мере загрузки, поэтому теперь файл обновляется и во время работы).
* При штатном выходе (`RunEvent::ExitRequested`/`Exit`) сессия сохраняется
  принудительно: `save_session_now`.
* При убийстве процесса без выхода теряется не больше ~5 секунд прогресса:
  после перезапуска эти куски просто докачаются заново, а не весь торрент.

## 3. Почему пропадало подменю

В `src/ui/menu.ts` обработчик наведения на обычный пункт меню закрывал все
открытые подменю:

```ts
button.addEventListener("mouseenter", () => closeSubmenus(0));
```

Он навешивался на **каждый** пункт, включая пункты внутри подменю. Курсор
доходил до первого варианта скорости («Без ограничения», «64 КиБ/с», …) —
срабатывал `mouseenter` — и `closeSubmenus(0)` удалял подменю вместе с самим
пунктом. Внешне это выглядело как «меню исчезает при наведении».

Исправление: у пункта есть глубина (`itemDepth` — сколько подменю над ним уже
открыто), и наведение закрывает только подменю **того же и более глубокого**
уровня:

```ts
button.addEventListener("mouseenter", () => closeSubmenus(itemDepth));
```

Тот же приём применён к открытию вложенных групп: `openSubmenu` закрывает
подменю начиная с уровня пункта, а не все подряд — иначе наведение на группу
внутри подменю закрывало бы её собственных предков.

Клавиатура не менялась: `ArrowRight`/`ArrowLeft`/`Esc` работают как раньше,
уровень панели теперь совпадает с `itemDepth + 1`.

## 4. Оптимистичный разчок

По BEP 3 клиент разчокивает не только лучших по отдаче нам, но и одного
случайного пира «на пробу». Без этого пир вне топ-8 никогда не получал от нас
данные, а его алгоритм отдачи так же никогда не разчокивал нас: новый быстрый
сид оставался задушенным навсегда.

Реализация (`crates/torrent-core/src/engine/torrent.rs`):

* в состоянии рантайма появился `optimistic: Option<u64>` и `optimistic_at`;
* раз в `OPTIMISTIC_INTERVAL = 30 с` (`TorrentHandle::tick` → `tick_optimistic`)
  выбирается случайный заинтересованный и задушенный нами пир вне топ-8;
* `should_unchoke` возвращает `true` и для него, `should_choke` — не душит его;
* выбор псевдослучайный на xorshift: новая зависимость `rand` не нужна.

## 5. Шифрование MSE/PE и uTP

В этой сборке их нет — и это осознанно, а не забывчивость:

* **MSE/PE** — отдельная подсистема: Diffie-Hellman 768 бит, RC4 с ключами из
  SHA-1, собственный state machine обмена, обёртка потока над `AsyncRead`/
  `AsyncWrite`, политика «шифровать/предпочитать/только открытым» и совместимость
  с тем, как это делает libtorrent. Проверить её можно только обменом с живым
  qBittorrent, а не моком: свой собственный «шифрованный пир» не доказывает
  совместимость.
* **uTP (BEP 29)** — ещё больше: потоки поверх UDP, LEDBAT-контроль перегрузки,
  выборочные подтверждения, MTU-обнаружение, таймеры повторов, идентификаторы
  соединений и связка с holepunch.

Писать их «на глазок» за один вечер — гарантированный способ получить подсистему,
которая молча не работает с настоящими пирами. Поэтому предлагаю так:

1. MSE/PE отдельным релизом, с вами в роли проверяющего: включаем режим
   «предпочитать шифрование, но открытые соединения не ломать», и вы смотрите
   на qBittorrent-пиров в реальном торренте.
2. uTP — после MSE, тоже отдельным релизом, с тестами на loopback между двумя
   экземплярами движка.

## 7. Ограничения

* При убийстве процесса теряется прогресс последних ~5 секунд (и только он).
* Отпечатки — размер и mtime. Если содержимое файла изменили, сохранив размер и
  время (редкий случай, например `SetFileTime`), карта будет применена ошибочно;
  полную гарантию даёт только проверка хэшами (кнопка «Перепроверить файлы»).
* Magnet-торренты всё равно качают метаданные заново: в сессии лежит ссылка, а
  не копия `.torrent`. После получения метаданных прогресс восстанавливается по
  карте, но время на сами метаданные тратится.
* Для торрентов, которые ещё ни разу не запускались, карты нет — первый запуск
  после обновления проверяет диск хэшами (один раз, вместо повторной загрузки).
