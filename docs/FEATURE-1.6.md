# Torrenta 1.6 — контракт доработки: DHT, PEX, веб-сиды, прокси, проброс порта, лимиты раздачи

Документ описывает, что именно вошло в версию 1.6.0, как это устроено внутри и какие
ограничения остались. Всё, что здесь написано, проверено кодом и тестами: если
поведение в коде отличается от текста, прав код, а не документ (и тогда документ
надо исправить).

## 1. Требования пользователя

Из отчёта по версии 1.4.0 были выбраны предложения P2 — «работа в сети без трекера,
через прокси и с пробросом порта»:

1. DHT (BEP 5) — поиск пиров без трекера.
2. PEX (BEP 11) — обмен адресами пиров между участниками раздачи.
3. Веб-сиды (BEP 19) — докачка кусков по HTTP с зеркал.
4. SOCKS5/HTTP-прокси для пиров и трекеров.
5. UPnP-IGD и NAT-PMP — автоматический проброс порта прослушивания.
6. Остановка раздачи по достижении ratio или лимита времени.

Пункт «uTP» из того же списка в 1.6.0 **не вошёл**: транспорт uTP (BEP 29) требует
полноценной реализации протокола поверх UDP (congestion control, SACK, повторные
передачи). Написать его «на глазок» и объявить работающим — значит соврать в
документации, поэтому uTP честно оставлен за рамками версии (см. раздел 10).

## 2. DHT (BEP 5) — `crates/torrent-core/src/dht.rs`

### 2.1 Что делает

Отдельный узел DHT на сессию. Узел говорит по KRPC (bencode поверх UDP), держит
таблицу узлов, кэш пиров и отвечает на входящие запросы `ping`, `find_node`,
`get_peers`, `announce_peer`.

```rust
pub const DEFAULT_BOOTSTRAP: &[&str];      // router.bittorrent.com, dht.transmissionbt.com, router.utorrent.com
pub struct DhtConfig { pub port: u16, pub bootstrap: Vec<String>, pub max_nodes: usize }
pub struct DhtStats { pub running: bool, pub nodes: usize, pub peer_cache: usize,
                      pub queries: u64, pub responses: u64 }
pub enum DhtError { Closed, Io(..), Timeout, Protocol(String), Remote(String) }
```

Публичный интерфейс: `Dht::new(config)`, `node_id()`, `start(&Arc<Self>) -> io::Result<u16>`,
`announce(InfoHash, u16)`, `take_peers(&InfoHash) -> Vec<SocketAddr>`, `stats()`, `shutdown()`.

### 2.2 Как устроено

* Идентификатор узла — 20 случайных байт, генерируются один раз при создании.
* Таблица — K-бакеты по общему префиксу идентификатора (K = 8), общий предел
  `max_nodes` (по умолчанию 1024). Живые узлы обновляются, мёртвые вытесняются.
* `start()` биндит UDP-сокет на `0.0.0.0:<port>`; `port = 0` — ОС выберет свободный,
  фактический номер возвращается из `start()` и попадает в настройки/статистику.
* Кэш пиров привязан к `InfoHash` и очищается по `take_peers`, поэтому один и тот же
  адрес не выдаётся движку дважды подряд.
* Токены `announce_peer` — `sha1(secret ++ ip)[..8]`; проверяется только IP
  отправителя, как и предписывает BEP 5.

### 2.3 Ограничения (честно)

1. `announce()` делает **один** раунд `get_peers` по 8 ближайшим узлам. Полного
   итеративного обхода Kademlia (когда спрашивают «соседей соседей» до сходимости)
   нет — на практике для популярных раздач этого достаточно, для редких медленнее.
2. `announce_peer` отправляется fire-and-forget: ответа не ждём, ошибка не влияет
   на результат `announce()`.
3. Секрет для токенов живёт весь процесс и не ротируется по времени.
4. Компактный список `nodes` (26 байт на узел) отдаётся только для IPv4; IPv6-пиры
   принимаются в `values` (18 байт), но в таблицу узлов не попадают.
5. Нет BEP 42 (secure node id) и защиты от Sybil-атак — узлы из чужих ответов
   добавляются как есть, это штатное поведение DHT.
6. Входящие сообщения с ключом `port` (пир просит наш DHT-порт, BEP 5 relay) не
   обрабатываются: мы не пересылаем `port` в свой узел, потому что узел локальный и
   адрес пира у нас уже есть из трекера/PEX.

### 2.4 Как DHT встроен в движок

* Узел **один на сессию** (`Inner.dht`), поднимается при старте менеджера, если
  `dht = true`; порт берётся из `dht_port` (`0` → свободный, фактический номер
  возвращается `start()` и попадает в статистику).
* Каждый торрент держит свой `Runtime::dht_loop`: раз в `DHT_POLL = 30 с` забирает
  `take_peers(info_hash)`, переводит адреса в `PeerAddr` и отдаёт в
  `add_candidates()` — дальше обычный путь: очередь пиров, подключение, обмен.
* Анонс `announce(info_hash, listen_port)` уходит сразу при первом тике и далее не
  чаще `DHT_ANNOUNCE = 300 с`, в отдельной задаче: сетевой раунд UDP не тормозит
  опрос пиров. При `listen_port == 0` (входящие недоступны) анонс пропускается.
* `shutdown()` менеджера останавливает узел; повторный вызов идемпотентен.
* Ограничение: в тестах узел не используется (живой сети нет), DHT покрыт только
  юнит-тестами модуля `dht`; во всех интеграционных конфигах стоит `dht: false`.

## 3. PEX (BEP 11) — `crates/torrent-core/src/pex.rs`

Модуль чистый, без сети: собирает и разбирает сообщение расширения `ut_pex`.

```rust
pub const EXT_PEX: u8 = 1;
pub struct PexMessage { pub added: Vec<SocketAddr>, pub dropped: Vec<SocketAddr> }
```

* `PexMessage::encode()` / `decode(&[u8])` — bencode-словарь с ключами `added`,
  `added.f`, `dropped`.
* `PexMessage::diff(known, fresh, dropped)` — что отправить пиру: только те адреса,
  которых он ещё не знает, плюс то, что выпало из среза.
* Лимит 50 адресов на поле (как в BEP 11): больше — ошибка `TooMany`, а не обрезка
  «на глазок».
* Фильтры `diff`: отбрасываются порт 0, `0.0.0.0`, `255.255.255.255`, multicast и
  IPv6; loopback и приватные адреса сохраняются (нужны для локальных тестов и LAN).
* Свой адрес в списке не определяется автоматически — вызывающий обязан передать его
  в `known`. Это делает движок, у которого есть адрес пира.

### 3.1 Как PEX встроен в движок

* Наш extended handshake объявляет `ut_metadata: 1` и `ut_pex: 2` (`OUR_UT_PEX = 2`).
  Идентификатор `ut_pex` **соседа** берётся из его `m`-словаря и запоминается в
  `PexSession { peer_addr, peer_id, known, last_sent, first }`.
* Входящее `Extended` с `ext_id`, совпавшим с нашим `ut_pex`, разбирается
  `PexMessage::decode` и отдаётся в `add_candidates()`; свой адрес и дубликаты
  отбрасываются. Ошибки разбора не рвут сессию — просто игнорируются.
* Исходящее — из общего цикла сессии на `Ev::Tick`: первый PEX уходит сразу после
  handshake, дальше не чаще `PEX_INTERVAL = 60 с`, до `PEX_MAX_ADDRESSES = 50`
  адресов за раз, через `PexMessage::diff(known, fresh, dropped)`.
* Настройка `pex = false` выключает и приём, и отправку; `ut_metadata` это не
  затрагивает.
* Ограничение: в e2e проверен только входящий путь (пир присылает PEX → движок
  скачивает с новых адресов); исходящий 60-секундный таймер тестом не покрыт.

## 4. Веб-сиды (BEP 19) — `crates/torrent-core/src/web_seed.rs`

```rust
pub struct WebSeedConfig { pub connect_timeout: Duration, pub read_timeout: Duration, pub max_parallel: usize }
pub struct WebSeed { .. }
impl WebSeed {
    pub fn new(url: &str, proxy: Option<&str>, config: WebSeedConfig) -> Result<Self, WebSeedError>;
    pub async fn fetch_range(&self, offset: u64, len: u32) -> Result<Vec<u8>, WebSeedError>;
    pub fn url(&self) -> &str;
}
pub fn parse_url_list(value: &Value) -> Vec<String>;
```

* `fetch_range` просит `Range: bytes=offset-(offset+len-1)`.
* Ответ `206` — разбирается `Content-Range`, проверяется, что начало совпало с
  запрошенным, читается ровно `len` байт; короче — `ShortBody`.
* Ответ `200` (сервер не умеет диапазоны) — поток пропускается до `offset` и
  читается `len` байт; это медленнее, но работает.
* `len == 0` — пустой вектор без сети. `416`/`404` — `Status(code)`, кривой диапазон —
  `BadRange`. `offset + len` считается через `checked_add`.
* `read_timeout` ограничивает ожидание заголовков и **каждого** куска тела, а не всего
  запроса целиком: иначе медленный, но живой сервер обрывался бы зря.
* Прокси — обычный `reqwest::Proxy::all`, TLS — rustls, редиректы ограничены пятью.
  Свой адрес и путь файла модуль не склеивает: это делает движок (у него есть
  `info.name`/`info.files[].path`).

### 4.1 Как веб-сиды встроены в движок

* `Metainfo.url_list` заполняется из верхнеуровневого `url-list` (строка или список,
  только `http`/`https`) в `metainfo::parse` и `from_raw_info`.
* Цикл `web_seed_loop` запускается только если `url_list` не пуст. Он берёт **один
  кусок за раз** и списывает под него бюджет у общего лимитера загрузки (блоками по
  16 КиБ), поэтому веб-сиды не обходят лимит скорости; пустой бюджет — сон
  `WEB_SEED_IDLE = 5 с`.
* Куски выбирает тот же `picker.pick`, что и пиры, по полной карте битфилда: кусок,
  который уже качается с пира, веб-сид не возьмёт, и наоборот.
* Данные проходят через `runtime.complete_piece(index, data)` — тот же путь, что у
  блока от пира: проверка SHA-1, запись на диск, счётчики и события.
* Любая ошибка (сеть, короткое тело, несовпадение хеша) — `picker.release`,
  ротация к следующему URL и пауза `WEB_SEED_RETRY = 5 с`. Запрос целиком ограничен
  `WEB_SEED_DEADLINE = 90 с`.
* Живые переключатели: выключенный `web_seeds` или пауза — сон 5 с без выхода из
  цикла; смена прокси пересобирает клиентов; выход — торрент завершён, список URL
  пуст или торрент остановлен.
* Ограничение: клиенты создаются только для `http`/`https` URL; таймауты (10 с
  соединение, 30 с чтение) и параллельность 4 — константы модуля, в `EngineConfig`
  не выведены, а цикл качает последовательно (чтобы не выбирать лимит целиком).

## 5. Прокси — `crates/torrent-core/src/proxy.rs`

```rust
pub enum ProxyKind { Socks5, Http }
pub struct ProxyConfig { pub kind: ProxyKind, pub host: String, pub port: u16,
                         pub username: Option<String>, pub password: Option<String> }
impl ProxyConfig { pub fn parse(raw: &str) -> Option<Self>; pub fn to_url(&self) -> String; }
pub fn connect(config: &ProxyConfig, target: SocketAddr) -> io::Result<TcpStream>;
```

* SOCKS5: приветствие `0x05`, методы `0x00` (без авторизации) и `0x02` (логин/пароль
  по RFC 1929), команда CONNECT (IPv4 и IPv6-литералы), коды ошибок переводятся в
  `io::ErrorKind`.
* HTTP: `CONNECT host:port HTTP/1.1`, `Proxy-Authorization: Basic …` (base64 написан
  локально по RFC 4648 — новых зависимостей нет), ожидается `200`, `407` →
  `PermissionDenied`.
* `to_url()` даёт строку для `reqwest::Proxy::all`.

### 5.1 Ограничения прокси

1. Только TCP (CONNECT). UDP ASSOCIATE и BIND не реализованы, поэтому **DHT и
   UDP-трекеры идут мимо прокси** — это прямая утечка реального IP, если прокси
   нужен для анонимности. Пользователь должен понимать это до включения.
2. SOCKS5 работает с IP-литералами (ATYP 0x01/0x04), потому что движок отдаёт уже
   разрешённые адреса пиров. Доменное имя по ATYP 0x03 не отправляется.
3. Схема `socks5h://` принимается, но remote-DNS на уровне пакета не реализован —
   ведёт себя как `socks5`.
4. HTTP-прокси: только Basic-auth. Тело ответа CONNECT не вычитывается по
   `Content-Length` — заголовки читаются побайтово до `\r\n\r\n`, чтобы не съесть
   начало туннеля.
5. `https://` принимается, но TLS до самого прокси не используется: для CONNECT
   схема не важна, а во внутреннем URL для reqwest (`ProxyConfig::to_url`) она
   нормализуется в `http://`. В настройках при этом остаётся ровно та строка,
   которую ввёл пользователь, — переписывания текста нет.

### 5.2 Как прокси встроен в движок

* Все исходящие TCP-подключения к пирам идут через единственную точку
  `peer::connect` → `proxy::connect`, если `proxy` задан. Прямой `TcpStream::connect`
  для пиров больше не используется.
* HTTP-клиент один на сессию (`Inner.http`: трекеры, веб-сиды, метаданные magnet) и
  пересобирается в `set_config` при смене прокси, поэтому настройка применяется на
  лету, без перезапуска торрентов.
* Невалидный адрес прокси `sanitized()` превращает в `None` — приложение продолжает
  работать напрямую, а не падает и не висит на «мёртвом» прокси. Причина пишется в
  stderr при сохранении настроек.
* UDP (DHT и UDP-трекеры) прокси не использует — см. ограничение 1 выше. Тестами
  покрыт парсинг/нормализация; живой прокси-сервер в CI не поднимается.

## 6. Проброс порта — `crates/torrent-core/src/port_map.rs`

```rust
pub enum MappingProtocol { Tcp, Udp }
pub struct PortMapping { pub gateway: IpAddr, pub external_port: u16,
                         pub protocol: MappingProtocol, pub lifetime: Duration }
pub fn map_port(internal_port: u16, protocol: MappingProtocol, lifetime_secs: u32) -> Option<PortMapping>;
pub fn unmap_port(mapping: &PortMapping);
```

* Сначала UPnP-IGD: SSDP M-SEARCH на `239.255.255.250:1900`, разбор `LOCATION`,
  выбор `WANIPConnection`/`WANPPPConnection`, SOAP `AddPortMapping`/`DeletePortMapping`.
* Если UPnP не ответил — NAT-PMP (RFC 6886): шлюз ищется эвристикой «локальный адрес
  UDP-сокета, подключённого к `8.8.8.8:53`, с последним октетом `.1`», запрос на
  порт 5351, три попытки с задержками 250/500/1000 мс.
* Внешний порт не подбирается: просим ровно внутренний. Занят — UPnP вернёт SOAP
  Fault, дальше пробуется NAT-PMP.
* Ошибки не паникуют: `map_port` возвращает `Option`, `unmap_port` молча
  игнорирует провал (best-effort).

### 6.1 Ограничения проброса

1. Живой прогон требует роутера с UPnP/NAT-PMP — автотест помечен `#[ignore]`.
   В CI проверяются только разбор XML/SOAP и байты NAT-PMP.
2. `PortMapping` не хранит внутренний порт: при удалении внешний порт отправляется в
   оба поля запроса. Это верно, пока внешний равен внутреннему (мы другого не просим).
3. NAT-PMP шлюз определяется эвристикой `x.y.z.1`; нетипичные шлюзы не покроются.
   Только IPv4.
4. IPv6-проброса (PCP, UPnP-IGDv2 с firewall hole punching) нет.

### 6.2 Как проброс встроен в движок

* При старте менеджера и при `set_config` (если `port_mapping = true`) выполняется
  `refresh_port_mapping`: `map_port(listen_port, Tcp, PORT_MAP_LIFETIME_SECS = 3600)`
  — пробрасывается только TCP, потому что входящие соединения пиров приходят по
  нему. UDP-порт DHT не пробрасывается: узел сам ходит наружу и не обслуживает
  входящие запросы (см. §2.3). Результаты складываются в `Inner.mapping`
  (`tokio::sync::Mutex<Vec<PortMapping>>`).
* `shutdown()` снимает все маппинги и останавливает DHT; ошибки только логируются.
* Держится время жизни 3600 с; отдельного продления по таймеру нет — маппинг
  переоформляется при следующем старте/`set_config`.
* Ограничение: событий и индикатора в интерфейсе нет, в тестах маппинг реально не
  выполняется (нет IGD) — проверяется только то, что путь не падает.

## 7. Лимиты раздачи

`TorrentSnapshot` получил два поля:

* `seed_ratio: f64` — `uploaded / downloaded`; если скачано 0 байт, ровно `0.0`
  (никаких `NaN`/`inf`, которые ломают сериализацию в JSON).
* `seed_limit_reached: bool` — торрент остановлен по лимиту и ждёт ручного
  возобновления.

Логика:

* Время раздачи копится только в состоянии `Seeding` и не идёт на паузе.
* Порог включающий: срабатывает при `ratio >= seed_ratio_limit` или
  `время >= seed_time_limit_min * 60`.
* Сработавший лимит снимает торрент с раздачи: `plan_kind()` возвращает `Idle`,
  торрент паркуется и не занимает seed-слот очереди.
* Ручной `resume`/`resume_all` сбрасывает и флаг, и накопленное время; `pause` и
  очередь только замораживают счётчик.
* В интерфейсе лимит виден: в строке списка — подпись «лимит раздачи · ×2,00», в
  панели деталей — плашка «Достигнут лимит раздачи — возобновите вручную».

## 8. Настройки версии 1.6

В `SettingsDto` (и, соответственно, в `settings.json`) добавлены поля, все с
`#[serde(default)]`, поэтому старый файл настроек читается без ошибок:

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `dht` | bool | `true` | узел DHT включён |
| `dht_port` | u16 | `0` | UDP-порт DHT; `0` — любой свободный |
| `pex` | bool | `true` | обмен пирами через PEX |
| `web_seeds` | bool | `true` | докачка с веб-сидов |
| `proxy` | string | `""` | `socks5://…` / `http://…`; пусто — без прокси |
| `port_mapping` | bool | `true` | проброс порта через UPnP/NAT-PMP |
| `seed_ratio_limit` | f64 | `0.0` | остановить раздачу при ratio ≥ N; `0` — без лимита |
| `seed_time_limit_min` | u32 | `0` | остановить раздачу через N минут; `0` — без лимита |

Нормализация при сохранении:

* прокси проверяется тем же `ProxyConfig::parse`, что и движок (единый источник
  правил); невалидная строка превращается в пустую с записью причины в stderr;
* `seed_ratio_limit` — только конечное и > 0, иначе `0.0` (закрывает `NaN`, `inf`,
  отрицательные);
* `dht_port` и `seed_time_limit_min` не зажимаются: `0` — это «любой»/«без лимита».

Видимая разница с UI: валидатор в интерфейсе **строже** движка — требует схему и
явный порт (`socks5://host:port`), тогда как движок подставил бы 1080/8080. Это
сделано намеренно: пользователь видит в поле ровно то, что уйдёт в движок.

## 9. Интерфейс (`src`)

* В «Настройках» появились две группы. «Сеть»: DHT, PEX, UPnP/NAT-PMP, веб-сиды
  (переключатели), «Порт DHT» и «Прокси» (поля). «Раздача»: «Ограничение по ratio» и
  «Ограничение по времени раздачи, мин».
* `proxyProblem()` проверяет строку прокси до сохранения: схема `socks5://` или
  `http(s)://`, непустой хост, порт в диапазоне 1–65535, поддержка
  `user:pass@host:port`.
* Список торрентов: у раздающих появился `×1,38` в подписи, у остановленных по
  лимиту — «лимит раздачи · ×2,00» и подсказка в `title`.
* Панель деталей: карточка «Рейтинг» показывает `×2,00` из `seed_ratio` (при нулевом
  скачанном — «—»), при сработавшем лимите появляется плашка
  «Достигнут лимит раздачи — возобновите вручную», а прогресс пишет
  «Раздача остановлена по лимиту».
* Новых CSS-токенов нет: используются существующие классы, поэтому проверка
  контраста осталась на 68 парах WCAG AA.

## 10. Что осталось за рамками версии

1. **uTP (BEP 29)** — транспорт не реализован; пиры по-прежнему только TCP. Обещать
   «uTP есть» было бы ложью, поэтому в 1.6.0 его нет.
2. DHT: один раунд `get_peers` без итеративного обхода, нет BEP 42, IPv4-only таблица.
3. PEX: IPv4-only, `added6`/`dropped6` не формируются (входящие игнорируются).
4. Прокси: только TCP, без UDP ASSOCIATE → DHT и UDP-трекеры идут напрямую. Это не
   «недоделка», а осознанное ограничение объёма: UDP-через-прокси требует отдельного
   туннеля и полноценного тестирования.
5. Проброс порта: без альтернативного внешнего порта, без IPv6/PCP, шлюз NAT-PMP по
   эвристике; живой прогон — ручной на роутере.
6. Лимиты раздачи: проверка идёт по тикеру (500 мс), поэтому момент остановки может
   отставать от порога на один тик; интеграционного теста на лимит по времени нет
   (ждал бы больше минуты) — проверяется юнит-тестами `SeedMeter`.
