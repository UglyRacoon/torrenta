# Архитектура Torrenta

Документ описывает устройство проекта: слои, потоки данных, задачи tokio и решения, которые определили текущую структуру кода. Публичный API ядра описан отдельно — в [CORE_API.md](CORE_API.md), продуктовая часть (экран, состояния, дизайн) — в [PRODUCT.md](PRODUCT.md).

## 1. Границы и слои

Проект — это Cargo-workspace из двух крейтов и отдельного фронтенда:

| Слой | Расположение | Отвечает за | Не знает о |
| --- | --- | --- | --- |
| Движок | `crates/torrent-core` | Протокол BitTorrent: bencode, метаданные, трекеры, пиры, куски, диск, DHT, PEX, веб-сиды, прокси и проброс порта | Tauri, DOM, окнах, настройках приложения |
| Обвязка | `src-tauri` | Окно, единственный экземпляр, команды `invoke`, события, настройки, привязка `.torrent` в реестре, жизненный цикл движка | Разметке и стилях интерфейса |
| Интерфейс | `src` | DOM, состояние экрана, форматирование, тема | Внутренностях движка — только `invoke` и события |

Правило зависимостей направлено в одну сторону: `src → src-tauri → torrent-core`. Обратных зависимостей нет, поэтому ядро можно тестировать и использовать без Tauri (`cargo test -p torrent-core`, `cargo build -p torrent-core`).

## 2. Ядро `torrent-core`

### 2.1 Модули

| Модуль | Роль |
| --- | --- |
| `bencode` | Разбор и сериализация bencode в собственное дерево `Value`. Никаких зависимостей от serde: протокол требует строгого порядка ключей. |
| `metainfo` | Разбор `.torrent`: `info`-словарь, информационный хэш (SHA-1 сырых байтов `info`), список файлов с раскладкой, куски, приватность (BEP 27). |
| `magnet` | Разбор magnet-ссылки: `xt=urn:btih` (hex и base32), `dn`, `tr`, `ws`. |
| `tracker` | Announce по HTTP(S) и UDP (BEP 3/15): сборка запроса, разбор ответа, компактные списки пиров (BEP 23), события started/stopped/completed. |
| `proxy` | Исходящий прокси для TCP: SOCKS5 (CONNECT, авторизация по RFC 1929) и HTTP CONNECT с `Basic`; разбор спецификации (`socks5`, `socks5h`, `http`, `https`), собственный `base64` — без новых зависимостей. Прокси применяется к соединениям с пирами, HTTP-трекерам и web seeds; UDP идёт напрямую. |
| `port_map` | Проброс порта на роутере: UPnP-IGD (SSDP-поиск, SOAP `AddPortMapping`/`DeletePortMapping`) и NAT-PMP, если IGD не нашёлся. Best effort: молчащий роутер — не ошибка. |
| `wire` | Peer wire protocol (BEP 3) и расширения (BEP 10): кодирование и разбор сообщений, handshake. |
| `pex` | PEX (BEP 11): кодирование и разбор `ut_pex`, дифф «добавить/удалить», компактные адреса по 6 байт, лимит 50. Сети не касается — только упаковка. |
| `dht` | DHT (BEP 5): KRPC поверх UDP, K-бакеты по 8 узлов, bootstrap, `get_peers` по info-hash и кэш найденных пиров. Один узел на сессию. |
| `web_seed` | HTTP-источники (BEP 19): разбор `url-list`, догрузка куска `Range`-запросом (`206` с проверкой `Content-Range`, `200` — диапазон вырезается из тела), таймауты и параллелизм в `WebSeedConfig`. |
| `bitfield` | Битовая карта кусков: установка, проверка, подсчёт, сериализация в формат протокола. |
| `peerid` | Peer id в стиле Azureus (BEP 20): `-TR1000-` + 12 символов. |
| `picker` | Выбор кусков: rarest-first, ограничение числа одновременных аренд, таймаут аренды (защита от «залипания» на медленном пире); выдаёт только «нужные» куски, а при заданных приоритетах файлов сначала перебирает куски высокого уровня, потом обычного, потом низкого. |
| `selection` | Выбор файлов и приоритеты: `Selection` (файлы → куски → объём), расчёт нужных кусков по смещениям, подсчёт скачанного по выбору, `effective_limit` (минимум глобального и торрентного лимита); `piece_levels` переводит `FilePriority` в уровни кусков, общий кусок получает максимум уровня. |
| `storage` | Работа с диском: перевод глобального смещения торрента в пару (файл, смещение внутри файла), чтение и запись без загрузки файла целиком; дескрипторы открываются с общим доступом на чтение/запись/удаление, а запись держится только пока торрент качает. |
| `engine` | Менеджер торрентов, рантайм одного торрента, очередь и лимиты активности, перепроверка данных, сессия с пиром, статистика, события, TCP-приём входящих подключений. |

### 2.2 Ключевые типы

- `TorrentManager` — единственная точка входа в движок: `new`, `preview_file`, `preview_magnet`, `add_file`/`add_file_with`, `add_magnet`/`add_magnet_with`, `set_file_selection`, `set_file_priorities`, `recheck`, `set_limits`, `pause`, `resume`, `pause_all`, `resume_all`, `remove`, `snapshot`, `totals`, `subscribe`, `shutdown`, `config`/`set_config`.
- `TorrentSnapshot` — плоский DTO для интерфейса: идентификатор, имя, info-hash, состояние, прогресс, скорости, действующие лимиты, число пиров, ETA, файлы (с признаком выбора и приоритетом), трекеры, подключённые пиры; с 1.6 — `seed_ratio` (отдано ÷ скачано, 0.0 при нулевом скачивании) и `seed_limit_reached` (лимит раздачи сработал, торрент ждёт ручного возобновления).
- `Metainfo` — разобранные метаданные торрента; в 1.6 появился `url_list` — HTTP-источники из ключа `url-list` (BEP 19), схемы фильтрует `web_seed::parse_url_list`, у magnet-торрента список пуст до получения метаданных.
- `AddOptions` — папка загрузки и индексы выбранных файлов при добавлении (приоритеты задаются отдельным вызовом `set_file_priorities`); `TorrentPreview`/`PreviewFile` — то же дерево файлов до добавления (для окна выбора).
- `TorrentState` — `Queued`, `Metadata`, `Checking`, `Downloading`, `Seeding`, `Paused`, `Completed`, `Error`.
- `FilePriority` — `Skip`, `Low`, `Normal` (по умолчанию), `High`; в `picker` превращается в уровень куска 0–2.
- `EngineConfig` — лимиты скорости и порта плюс `max_active_downloads`/`max_active_seeds` (0 — без ограничения), очередь считает их при каждой смене состояния; с 1.6 здесь же сетевые настройки: `dht` и `dht_port` (0 — свободный UDP-порт), `pex`, `web_seeds`, `proxy` (строка спецификации; пустая или нерабочая означает «выключено»), `port_mapping`, `seed_ratio_limit`/`seed_time_limit_min` (0 — без ограничения).
- `EngineEvent` — мгновенные события для интерфейса: `Added`, `StateChanged`, `Completed`, `Error`, `Removed`.
- `Stats` — атомарная статистика торрента: `AtomicU64`/`AtomicU32` для счётчиков, `RwLock` для полей, которые меняются редко и целиком (имя, файлы, трекеры, пиры).
- `Flags` — `AtomicBool` паузы и удаления: циклы проверяют их между шагами и не требуют блокировок.
- `Dht`/`DhtConfig` — узел DHT: `start`/`shutdown`, `announce` (один раунд `get_peers` по ближайшим узлам) и `take_peers` (забрать кэш адресов по info-hash); `DhtConfig` задаёт UDP-порт, bootstrap-адреса и пределы таблицы.
- `PexMessage` — `encode`/`decode`/`diff` для `ut_pex`: сокетов и таймеров внутри нет, адреса приходят и уходят через `engine`.
- `WebSeed`/`WebSeedConfig` — один HTTP-источник: `fetch_range` забирает диапазон внутри куска, ошибки — в `WebSeedError`; таймауты (`connect_timeout`, `read_timeout`) и `max_parallel` — в конфиге.
- `ProxyConfig`/`ProxyKind` — разбор и нормализация строки прокси; `connect` открывает туннель до адреса пира и возвращает обычный `TcpStream`.
- `PortMapping`/`MappingProtocol` — что именно проброшено: шлюз, внешний порт, протокол и срок аренды; эти же данные нужны, чтобы снять запись.

### 2.3 Один торрент — один рантайм

На каждый добавленный торрент создаётся `Runtime` (`engine/torrent.rs`), который владеет:

- текущим состоянием и флагами паузы/удаления,
- счётчиками и списком пиров,
- арендами кусков (`picker`),
- собственными ведрами скорости и ссылкой на общий лимитер сессии (`SharedLimiters` в `Inner`): действующая скорость — минимум глобального и торрентного лимита, общее ведро делится между всеми торрентами,
- выбранными файлами (`Selection`): нужные куски, объём выбора и уровни приоритетов для `picker`,
- режимом доступа к файлам: пока торрент качает, дескрипторы открыты на запись; на паузе, в очереди, после завершения и во время проверки — только на чтение (`Storage::release_writes`/`acquire_writes`),
- задачами опроса DHT и догрузки с web seeds (`dht_loop`, `web_seed_loop`): они появляются, только если включены настройками и применимы к торренту (есть метаданные, есть `url-list`), и живут ровно столько же, сколько торрент,
- каналами событий `have_tx` (broadcast, чтобы все сессии узнавали о новых кусках) и `events` (broadcast в `TorrentManager`).

## 3. Потоки данных

### 3.1 Добавление `.torrent`

1. `preview_torrent` получает байты из интерфейса (файл, перетаскивание или `pick_torrent_files`) и вызывает `preview_file`: `metainfo::parse` строит `TorrentPreview` — имя, размер, файлы, трекеры, ничего не добавляя.
2. Интерфейс показывает окно выбора: папка загрузки и галочки по файлам (по умолчанию все).
3. `add_torrent` передаёт те же байты и `AddOptions` (папка + индексы выбранных файлов) в `add_file_with`.
4. `metainfo::parse` разбирает bencode, строит `Metainfo`, считает info-hash по сырым байтам `info`.
5. Проверяется дубликат по info-hash, строится `Selection` по выбранным файлам, создаётся `Runtime` в состоянии `Queued`/`Downloading`.
6. `storage` раскладывает непрерывный поток на файлы и готовит их на диске; планировщик запрашивает только нужные куски. Проверки уже лежащих данных при добавлении нет: торрент считается не скачанным, куски запрашиваются заново. Проверить диск можно явно — командой «Перепроверить файлы» (`recheck`, раздел 3.7).
7. `TorrentManager` отправляет `EngineEvent::Added`, интерфейс получает обновление на следующем тике.

### 3.2 Добавление magnet-ссылки

1. `preview_magnet` (`preview_torrent` с magnet-источником) идёт за метаданными так же, как `metadata_task`, но без регистрации торрента: до 5 трекеров по очереди, ограниченное время, проверка info-hash. Если метаданные получить не удалось, интерфейс всё равно даёт добавить ссылку «как есть».
2. `add_magnet_with` разбирает ссылку: info-hash, `dn`, список трекеров; `AddOptions` задаёт папку и выбранные файлы (для magnet без списка файлов выбор применяется, как только метаданные получены).
3. Торрент появляется в списке в состоянии `Metadata` — метаданных ещё нет, известен только info-hash.
4. Запускается `metadata_task`: торрент анонсируется на трекерах и подключается к найденным пирам с поддержкой расширений.
5. По BEP 10 согласуется `ut_metadata` (BEP 9), метаданные забираются кусками, склеиваются и проверяются: SHA-1 полученного `info`-словаря должен совпасть с info-hash из ссылки.
6. Совпало — `Metainfo` построен, применяется выбор файлов и отложенные приоритеты (`pending_priorities`), торрент переходит в `Downloading` (или в `Queued`, если слот занят) и дальше работает как обычный `.torrent`. Не совпало — состояние `Error` с понятным сообщением.

### 3.3 Трекеры и пиры

1. Для каждого URL трекера торрент запускает `tracker_loop`: первый announce с `event=started`, дальше по интервалу из ответа.
2. Ответ (HTTP или UDP) даёт список адресов пиров; адреса добавляются в известные (`peers_known`). Источник не важен: адреса из DHT (§3.8) и PEX (§3.9) попадают в ту же очередь подключения через `add_candidates`.
3. Коннектор держит не больше `max_peers_per_torrent` активных соединений: на каждого пира — handshake, проверка info-hash, затем сессия.
4. Помимо исходящих соединений работает TCP-приём: если порт прослушивания доступен, входящие handshake обрабатываются так же, как исходящие (`handle_incoming`).
5. По завершении загрузки отправляется announce с `event=completed`, при удалении — `event=stopped`.
6. Сбой объявления не теряется: `failure reason` от трекера и две сетевые ошибки подряд переводят торрент в `Error` с русским текстом (только пока нет ни скачанных байт, ни подключённых пиров), а первое успешное объявление снимает ошибку и возвращает загрузку.
7. `pause`/`resume` работают без ожидания трекера: при возобновлении известные адреса пиров возвращаются в очередь подключения (`requeue_peers`).

### 3.4 Куски: от запроса до диска

1. `picker` выдаёт очередной кусок: сначала куски высокого уровня (приоритет файлов), внутри уровня — самые редкие, с учётом того, у кого они есть и что уже запрошено у других; куски низкого уровня запрашиваются только когда более важных не осталось.
2. Кусок запрашивается блоками; пришедшие блоки собираются в буфер.
3. Когда кусок собран, считается SHA-1 и сравнивается с хэшем из метаданных.
4. Успех — блок записывается через `storage` по нужным файлам и смещениям, в `bitfield` ставится бит, `have_tx` рассылает номер куска сессиям (чтобы пиры узнали, что кусок у нас есть, и мы перестали его запрашивать).
5. Ошибка хэша — кусок отбрасывается, аренда возвращается в пул, а сам кусок откладывается на `1500 мс × число неудач` (максимум 10 с): остальные куски загружаются дальше, а зависнуть на одном испорченном торрент не может — когда доступных кусков больше нет, «остывающие» берутся снова.
6. Все нужные куски на месте — состояние `Completed`/`Seeding`, `EngineEvent::Completed`. При выборочной загрузке «все куски» означают все куски выбранных файлов, поэтому `pieces_have` может быть меньше `piece_count`. В этот момент движок сбрасывает данные на диск, отпускает запись и переоткрывает файлы только для чтения.

### 3.5 Статистика и события до интерфейса

1. Сессии пиров увеличивают счётчики трафика и `have_bytes` только за проверенные куски: `downloaded` — полезные байты, прошедшие SHA-1, поэтому у завершённого торрента он равен размеру; `Stats::sample` раз в интервал пересчитывает скорости по дельтам.
2. Тикер в `src-tauri` (см. ниже) каждые 500 мс собирает `Vec<TorrentSnapshot>` и отправляет событие `engine://state`.
3. Мгновенные события движка транслируются в `engine://event` — по ним интерфейс показывает тосты, не дожидаясь тика.
4. Обратный отсчёт автовыключения приходит отдельным событием `engine://auto-shutdown` (см. 4.2).

### 3.6 Выборочная загрузка, приоритеты и лимиты скорости

1. `Selection::from_files` переводит индексы файлов в набор «нужных» кусков: кусок нужен, если пересекается с выбранным файлом хотя бы одним байтом (последний кусок торрента обычно короче).
2. `Selection::piece_levels` строит те же куски из `FilePriority`: `Skip`/`Low` → уровень 0, `Normal` → 1, `High` → 2; если кусок покрывает несколько файлов, берётся максимальный уровень. `picker` получает уровни и перебирает их от старшего к младшему, не арендуя куски `Skip`.
3. `picker` получает предикат «нужен ли кусок» и не арендует ненужные; сеть о них не узнаёт.
4. Смена выбора (`set_file_selection`) или приоритетов (`set_file_priorities`) выполняется на лету: аренды ненужных кусков освобождаются, их буферы выбрасываются, `progress`/`eta` пересчитываются по новому объёму, а трекер получает свежий `left`. Если из-за сужения выбора все нужные куски уже на месте, `wake_announcer` будит цикл трекера, и `event=completed` уходит сразу, а не через интервал объявления (побудка сделана флагом `announce_pending` с опросом раз в 500 мс, чтобы сигнал не терялся, пока ответ трекера в пути).
5. Лимиты: у торрента своё ведро (`RateLimiter`), у сессии — общее. Запрос проходит своё ведро, затем общее; действующая скорость — `min(глобальный, торрентный)`, где `0` означает «без ограничения». Поэтому глобальный потолок делится между всеми торрентами, а не выдаётся каждому.

### 3.7 Очередь, лимиты активности и перепроверка

1. `TorrentManager::schedule` вызывается при каждом изменении состава списка или флагов: он строит план (`plan`) из текущих состояний и лимитов `max_active_downloads`/`max_active_seeds` (0 — без ограничения). Загрузки и раздачи считаются отдельно: торрент, который качает, занимает слот загрузки, готовый — слот раздачи.
2. Кандидаты сортируются по времени добавления (`added_at`, затем `id`) и активируются до заполнения лимита: `activate` снимает паузу, выставляет состояние и забирает файлы на запись. Остальные паркуются (`park`): пауза движка, `Queued`, запись отпущена.
3. Ручная пауза сильнее очереди: `user_paused` торрент план не занимает и сам не запускается; `resume`/`resume_all` только снимают флаг и снова отдают решение планировщику — лишние снова окажутся в `Queued`.
4. `schedule` вызывается после любого изменения состава списка, флагов, выбора файлов и лимитов, а также каждый тик статистики — поэтому слот освобождается и занимается сам, без участия интерфейса, даже когда торрент завершился «сам по себе».
5. `recheck(id)` переводит торрент в `Checking`, обнуляет `pieces_have`, останавливает обмен и отпускает запись; затем `verify_all` читает каждый кусок из `Storage`, сравнивает SHA-1 с эталоном из метаданных и восстанавливает битовую карту. Прогресс виден как `pieces_have` от 0 до `piece_count` (`eta_seconds = 0`), повторный вызов во время проверки — идемпотентный `Ok(())`. После проверки состояние выбирается по факту: `Seeding`/`Completed`/`Downloading`, а пользовательская пауза сохраняется; если загрузка продолжается, запись забирается обратно (`acquire_writes`).
6. Перепроверка не переподключает пиров и не трогает известные адреса: обмен просто возобновляется после неё.

### 3.8 DHT (BEP 5)

1. Узел один на сессию: `TorrentManager` держит его в `Inner.dht`, а `refresh_dht` поднимает и гасит его при старте, смене настроек и остановке. Порт — `dht_port` (0 — свободный); занятый UDP-порт не ошибка: узел просто не стартует, а торренты остаются на трекерах и PEX.
2. `dht_loop` — отдельная задача на торрент. Раз в 30 с она забирает `take_peers(info_hash)` и отдаёт адреса в `add_candidates` — тот же коннектор, что и для пиров с трекеров, дальше источник ни на что не влияет.
3. Анонс своего порта: сразу после старта (метаданные к этому моменту уже есть), дальше раз в 5 мин. Вызов идёт отдельной задачей, поэтому сетевой раунд не задерживает следующий опрос. При `listen_port == 0` анонс пропускается — сообщать нечего, но опрос `get_peers` продолжается.
4. Остановка движка передаётся узлу через `refresh_dht`: цикл выходит по флагу, `shutdown` гасит сокет, и UDP-порт освобождается вместе с сессией.

### 3.9 PEX (BEP 11)

1. В расширенном handshake объявлены `ut_metadata: 1` и `ut_pex: 2`; из `m` пира берём его номер `ut_pex` и запоминаем в сессии. Пир расширение не объявил — PEX с ним просто не работает, остальное общение не меняется.
2. Входящее `ut_pex` разбирает `pex::decode`, поле `added` уходит в `add_candidates`; `dropped` игнорируется — адреса и так выбывают, когда подключение не удалось.
3. Исходящее — из того же цикла сессии (`Ev::Tick`, 250 мс): первый пакет уходит сразу после handshake, следующие — не чаще раза в 60 с, не больше 50 адресов за раз. Состав считает `PexMessage::diff` по известным адресам, поэтому в пакет попадают только новые и отвалившиеся.
4. `ut_metadata` при этом не тронут: PEX — отдельный канал с тем же механизмом расширений, и обмен метаданными работает по-прежнему.

### 3.10 Веб-сиды (BEP 19)

1. `web_seed_loop` создаётся только если в метаданных есть `url_list`; настройка `web_seeds` — единственный выключатель, отдельного списка URL в интерфейсе нет.
2. Куски берутся по одному и тем же `picker`, что и у пиров (битовая карта «нужно всё», свой набор исключений пуст): занятый web seed'ом кусок больше никто не запросит, двойной загрузки нет.
3. Скорость списывается с общего лимитера блоками по 16 КиБ, так что web seeds подчиняются тем же лимитам, что и пиры.
4. Скачанные байты идут общим путём `complete_piece`: SHA-1, запись на диск, счётчики и `have_tx`. Отличие от пира только в транспорте.
5. Ошибка, таймаут (90 с на кусок) или несовпадение хэша — аренда освобождается, URL берётся следующий по кругу, пауза 5 с; один плохой источник не блокирует торрент.
6. Переключения на лету: выключение настройки усыпляет цикл (он остаётся жив и проснётся), смена прокси пересобирает источники, пауза торрента останавливает загрузку.

### 3.11 Прокси и проброс порта

1. Исходящие соединения к пирам идут через `peer::connect`: при заданном `proxy` — через `proxy::connect` (SOCKS5 CONNECT или HTTP CONNECT), иначе напрямую. Входящие прокси не используют: их принимает наш сокет.
2. HTTP-клиент сессии (`HttpClient` в `Inner`) собирается `build_http` под текущий прокси; им пользуются трекеры, `metadata_task` и предпросмотр magnet. Web seeds строят свой клиент из той же строки, поэтому смена прокси в `set_config` доходит до всех HTTP-запросов без перезапуска торрентов.
3. UDP идёт напрямую: SOCKS5 `UDP ASSOCIATE` не реализован, а HTTP-прокси UDP не умеет вовсе. Это ограничение протокола, а не недоделка, и оно записано в документации настройки.
4. Проброс порта — best effort: `refresh_port_mapping` вызывается при старте, при `set_config` и в `shutdown`. Пока настройка включена и порт слушается, ставится `map_port(listen_port, Tcp, 3600)`, при выключении и остановке записи снимаются `unmap_port`.
5. Ошибка проброса не влияет на работу: нет IGD, роутер молчит или запрещает — движок работает без проброса и ошибку не показывает. Внешний адрес нигде не сохраняется, интерфейс о нём не знает.

### 4.1 Тикер и «отпечатки» состояния

Снимок отправляется не по таймеру «всегда», а только когда это имеет смысл:

- **живой отпечаток** (`dynamic`) — прогресс в промилле, скорости, число пиров; меняется постоянно, пока идёт загрузка;
- **значимый отпечаток** (`significant`) — состояния (включая `queued`/`checking`), ошибки, состав списка, флаги выбора и приоритеты файлов; меняется редко.

Живые изменения уходят на каждом тике (500 мс), значимые — не чаще раза в секунду. Если не изменилось ничего, событие не отправляется; интерфейс не просыпается зря, а загрузка CPU на простое близка к нулю.

### 4.2 Автовыключение

1. Переключатель в статус-баре вызывает `set_auto_shutdown(enabled)`; флаг `auto_shutdown` пишется в `settings.json` тем же атомарным механизмом, что и остальные настройки, поэтому включённое автовыключение переживает перезапуск.
2. Фоновый цикл (500 мс) смотрит на `Vec<TorrentSnapshot>`: «все загрузки завершены» = флаг включён, есть хотя бы один торрент в `Completed`/`Seeding` и нет ни одного в `Queued`, `Metadata`, `Downloading`, `Paused`.
3. Условие выполнено — один раз запускается `shutdown.exe /s /t 60 /c "Torrenta: все загрузки завершены"` и начинается отсчёт; каждую секунду уходит `engine://auto-shutdown { pending_seconds }`. Если появилась новая загрузка (или пользователь нажал «Отменить»), вызывается `shutdown.exe /a`, а событие сообщает `null`.
4. `cancel_auto_shutdown` дополнительно сохраняет `auto_shutdown = false`, чтобы после перезапуска система не выключилась «сама».
5. Ограничение: выключение инициируется системной командой; при отказе (нет прав, политика) текст ошибки приходит в интерфейс тостом, а таймер сбрасывается.

### 4.3 Трей, автозагрузка и поведение окна

Три настройки из `settings.json` — `autostart`, `start_minimized`, `close_to_tray` — относятся только к оболочке: в `EngineConfig` они не входят, движок о них не знает.

1. Окно `main` создаётся скрытым (`"visible": false`). В `setup` оно показывается, если `start_minimized == false`; при запуске «в трее» окно ждёт в скрытом состоянии. Если значок в трее создать не удалось, окно показывается принудительно — иначе до приложения было бы не добраться.
2. Значок в трее создаётся всегда, потому что он нужен обоим сценариям: и запуску свёрнутым, и закрытию в трей. Ошибка `TrayIconBuilder` только логируется.
3. Закрытие окна перехватывается один раз в `setup`: обработчик читает `close_to_tray` в момент события, поэтому переключатель в настройках работает без перезапуска. Флаг включён — `api.prevent_close()` и `hide()`, загрузки продолжаются, а выйти можно пунктом «Выход» меню трея (`app.exit(0)`); флаг выключен — окно закрывается штатно и приложение завершается, как в 1.1.
4. Автозагрузка синхронизируется при каждом старте (`autostart::apply(settings.autostart)`), а не только в момент переключения: так запись в реестре обновляет путь к exe после обновления программы и не остаётся «висеть» после выключения опции. Идемпотентность даёт `reg.exe add ... /f`, а удаление отсутствующего значения не считается ошибкой (`reg query` подтверждает, что записи нет).
5. При сохранении настроек (`AppEngine::apply_settings`) автозагрузка применяется **до** записи `settings.json`. Если `reg.exe` вернул ошибку, настройки не меняются ни в памяти, ни в файле — галочка в интерфейсе не расходится с реестром. Если ошибкой завершилась уже запись файла, запись в реестре откатывается к прежнему значению.
6. Ограничения: автозагрузка — только ветка `HKCU`, то есть для текущего пользователя и без прав администратора; общий для всех пользователей автозапуск и служба не поддерживаются. На не-Windows платформах модуль — заглушка, чтобы код собирался.

### 4.4 Один экземпляр и открытие `.torrent` из Проводника

Windows запускает новую копию `.exe` на каждый двойной щелчок по ассоциированному файлу, поэтому единственность экземпляра и приём источника — одна задача, решаемая вместе:

1. `tauri-plugin-single-instance` регистрируется **первым** плагином: он проверяет наличие работающего процесса до создания окон и остальных плагинов. Второй запуск передаёт свой `argv` и `cwd` в колбэк первого приложения и завершается сам.
2. Колбэк разбирает аргументы чистой функцией `source_from_args(argv, Some(cwd))`: `magnet:` (без учёта регистра) возвращается как есть, путь с расширением `.torrent` — тоже, относительный путь склеивается с каталогом запуска только если файл существует. Флаги и мусорные аргументы игнорируются.
3. Источник кладётся в `PendingOpen` (`Mutex<Option<String>>`, устойчив к «отравлению»), окно показывается и получает фокус (`tray::show_main`), а в интерфейс уходит сигнальное событие `engine://open-source` без полезной нагрузки. Если аргументов-источников нет (просто повторный запуск ярлыка), окно только показывается.
4. Интерфейс при инициализации сначала подписывается на событие, затем **безусловно** вызывает `take_open_request` — так забирается источник самого первого запуска, когда событие ушло до подписки. Take-once гарантирует, что диалог добавления не откроется дважды.
5. Путь запуска, когда Torrenta не работает, обрабатывается в `setup` тем же `queue_open`, но с `base = None`: источник передаётся напрямую, без склейки относительных путей.
6. Ассоциация `.torrent` больше не зависит от установщика: с 1.7.0 приложение проверяет и при необходимости правит её само (`association.rs`, см. 4.9), потому что после обновления в реестре оставался путь к старой сборке, а ключ с пустым `ProgId` вообще гасил двойной клик. `tauri.conf.json` (`bundle.fileAssociations`, ProgID `BitTorrent`, команда `"...\torrenta.exe" "%1"`) остаётся объявлением для бандлера: NSIS пишет ассоциацию в `HKCU\Software\Classes` без прав администратора, MSI/WiX поддерживает её неполно. Источник истины для приложения — реестр, прочитанный при старте.
7. Выход в интерфейсе и в меню трея — это команда `quit_app` / пункт «Выход» → `app.exit(0)`: процесс завершается всегда, настройка `close_to_tray` на них не действует (она влияет только на крестик окна).

### 4.5 Сессия и восстановление списка

1. Хранилище — каталог `session` в каталоге конфигурации приложения: `session.json` со списком и `session-data/<info_hash>.torrent` с копиями метаданных. Сессия отделена от `settings.json`: настройки читаются синхронно, а список торрентов нужен движку и может меняться в любой момент.
2. Источник запоминается при добавлении: `add_torrent` после успешного добавления кладёт в `SessionRegistry` либо исходные байты `.torrent`, либо magnet-ссылку (и копию файла на диск). Торренты из папки наблюдения регистрируются так же.
3. Запись — в тикере состояния: не чаще раза в 2 с и только при изменении `payload_hash` (сериализованный список без прогресса). В файл попадают источник, папка загрузки, ручная пауза, выбранные файлы, отличия приоритетов и лимиты скорости; прогресс, скорости и ETA не пишутся, иначе диск дёргался бы каждые полсекунды. Запись атомарна (`tmp` + `sync_all` + `rename`), при выключенном `restore_session` не идёт вовсе.
4. Чтение — в фоновой задаче после показа окна (`spawn_session_restore`): настройка читается один раз, файловые торренты добавляются из копии метаданных, magnet — по ссылке, затем применяются пауза, лимиты и приоритеты. Ошибка одной записи (нет копии, файл повреждён, торрент уже добавлен) не прерывает остальные: она пропускается, счётчики `restored`/`skipped` пишутся в журнал одним итогом.
5. Имя копии при чтении вычисляется из `info_hash` (40 шестнадцатеричных символов), а не берётся из JSON: подменённый путь не выйдет за пределы `session-data`.
6. Ограничения: magnet после перезапуска не знает имени и размера, пока не получит метаданные заново, а приоритеты `Low`/`High` у него не восстанавливаются; несуществующая папка загрузки заменяется каталогом по умолчанию.

### 4.6 Папка наблюдения

1. Задача `watch::spawn` читает настройку `watch_dir` на каждом тике, поэтому папку можно включать, менять и выключать без перезапуска; пустая строка означает «выключено».
2. Раз в 3 с каталог просматривается по верхнему уровню: берутся только файлы с расширением `.torrent`, обычные (не каталог и не ссылка), непустые и не менявшиеся последние 2 с — так недописанный браузером файл не читается наполовину. Кандидаты сортируются по именам, порядок добавления предсказуем.
3. Файл добавляется в папку загрузки из настроек и регистрируется в сессии, затем переносится в `<watch_dir>/done`. Туда же отправляется и файл, который добавить не удалось (пустой, повреждённый, уже добавлен): иначе ошибка повторялась бы каждый тик. Имена в `done` не перезаписываются — при совпадении добавляется ` (2)`, ` (3)`.
4. Перенос — `rename`, при переходе между дисками или занятом файле — копирование с удалением. Одинаковые сообщения журнала печатаются один раз (`LoudOnce`), поэтому недоступная папка не заливает stderr.

### 4.7 Уведомления и подсказка трея

1. Уведомление о завершении показывает `lib.rs` из обработчика `EngineEvent::Completed`: плагин `tauri-plugin-notification`, заголовок «Torrenta», текст «Имя» загружен». Условия — включённая настройка `notify_on_complete` и главное окно не видимо или не в фокусе; ошибки показа только логируются.
2. Подсказка значка обновляется из тикера не чаще раза в 2 с и дополнительно при смене текста (значок могут пересоздать). Текст: `Torrenta — ↓ 4,2 МБ/с · ↑ 512 КБ/с · 3 из 5` при активных загрузках и `Torrenta — нет активных загрузок` в остальных случаях; длина обрезается по символам до 120, чтобы не рвать кириллицу.

### 4.8 Порядок инициализации и новые команды

Порядок шагов в `run`/`setup` задан зависимостями: каждый следующий шаг пользуется результатом предыдущего, а сбой реестра или диска не должен отменять запуск.

1. Плагин `single-instance` регистрируется первым: проверка «приложение уже запущено» должна пройти до создания окон и остальных плагинов, иначе второй экземпляр успеет открыть своё окно. Следом подключаются `dialog`, `opener`, `notification` и `updater`.
2. `settings::resolve_data_dir(exe_dir, app_config_dir)` выбирает каталог данных один раз; результат (`dir` плюс признак `portable`) получают настройки, сессия и `AppEngine`, поэтому `settings.json` и `session/` всегда лежат вместе.
3. Настройки читаются из этого каталога (`settings::load` не падает никогда), `download_dir` создаётся — при ошибке только пишется строка в stderr, — затем `settings::to_engine_config` и `TorrentManager::new`.
4. `manage(AppEngine)` → `manage(SessionRegistry)` → `manage(single_instance::PendingOpen)`: команды и колбэк плагина должны застать состояние на месте.
5. Тема применяется к окну, созданному из конфигурации ещё до `setup`; создаётся значок в трее, синхронизируется автозагрузка (`autostart::apply`).
6. Привязка `.torrent`: `association::current_exe()` → `ensure` при включённом `associate_files`, иначе только `status`; итог кладётся в `manage(AssociationSlot)`, а причина неудачи печатается в stderr. Ошибки реестра старт не отменяют.
7. Окно показывается, если не включён запуск в трей или значок создать не удалось; на него вешается перехват закрытия.
8. Стартовые аргументы (`single_instance::source_from_args`) кладутся в `PendingOpen`: событие в этот момент может потеряться, поэтому интерфейс забирает запрос командой `take_open_request`.
9. Запускаются фоновые задачи — тикер состояния, трансляция событий, автовыключение, восстановление сессии, папка наблюдения.
10. `invoke_handler` регистрирует 34 команды: 33 из `commands` и `single_instance::take_open_request`.

Новые в 1.7.0 команды:

| Команда | Что делает |
| --- | --- |
| `set_torrent_sequential(state, id, on)` | Включает последовательную загрузку торрента: куски отдаются по порядку вместо rarest-first. Работает и для magnet без метаданных — флаг применится, как только появится рантайм. Значение по умолчанию для новых торрентов берётся из настройки `sequential`, а выбор по конкретному торренту живёт в памяти движка и после перезапуска не восстанавливается. |
| `torrent_trackers(state, id)` | Текущий список трекеров торрента. |
| `set_torrent_trackers(state, id, urls)` | Заменяет список трекеров; разбор и проверка схемы — в ядре, ошибка приходит готовой строкой. |
| `reannounce_torrent(state, id)` | Внеочередной аннонс на всех трекерах торрента. |
| `engine_diagnostics(state)` | Снимок диагностики: порт прослушивания, DHT/PEX/web seeds, прокси, проброс порта, окно расписания, лимиты, `sequential`, торренты, пиры, скорости, время работы. |
| `portable_info(state)` | `{ portable, data_dir }` — где лежат данные (см. 4.10). |

| `repair_association(state, slot)` | Принудительно регистрирует Torrenta обработчиком; живой чужой обработчик по-прежнему не перехватывается (см. 4.9). |

`DiagnosticsDto` повторяет `torrent_core::Diagnostics` поле в поле и остаётся в `snake_case`. `AssociationDto` — единственный DTO слоя Tauri с `#[serde(rename_all = "camelCase")]` (ключи `available`, `handler`, `command`, `isOwner`, `repaired`, `message`): контракт закреплён тестом, который сравнивает полный набор ключей, поэтому переименование поля ломает тест, а не интерфейс.

Синхронные команды Tauri выполняются на главном потоке, поэтому блокирующая работа уходит в `tauri::async_runtime::spawn_blocking`: чтение `.torrent`-файла в `preview_torrent` и `add_torrent` и все обращения к реестру ассоциаций (`association_status`, `repair_association` и внутренний `ensure` из `set_settings`). `check_update` наоборот `async` без блокировки — сеть ждёт плагин, а не поток команд.

### 4.9 Ассоциация `.torrent`: слои реестра и самоисцеление

Причина появления `association.rs` — реальный баг: при переходе с 1.3.1 на 1.7.0 двойной щелчок по `.torrent` поднимал старую сборку вместо окна добавления. В реестре оставался выбор пользователя с `ProgId = Applications\torrenta.exe`, а сам ключ приложения указывал на путь прежней версии. Второй вариант поломки — `UserChoiceLatest` с пустым `ProgId`: Windows в этом случае не открывает ничего и даже не показывает диалог выбора программы.

Обработчик читается послойно, сверху вниз; первый найденный слой и есть фактический:

1. `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\FileExts\.torrent\UserChoiceLatest` — слой Windows 11, значение `ProgId`. Ключ есть, а значение пустое → `HandlerSource::EmptyChoice(UserChoiceKey::Latest)`.
2. `...\UserChoice` — классический выбор пользователя (`ProgId`; `Hash` пишет только оболочка).
3. `HKCU\Software\Classes\.torrent` — значение по умолчанию, то есть ProgID, который пишет установщик; это `HandlerSource::Classes`. Ничего не найдено — `HandlerSource::Missing`.
4. Команда открытия берётся из `HKCU\Software\Classes\{progid}\shell\open\command`, при отсутствии — из `HKLM`: установщики уровня машины пишут туда.

`HandlerView { progid, command, source }` — снимок этого чтения, `UserChoiceKey` (`Latest`/`Current`, метод `reg_path`) называет конкретный слой выбора.

Решение принимает чистая функция `decide(&HandlerView, exe) -> Decision` — без реестра, поэтому проверяется юнит-тестами:

- пустой `ProgId` в слое `UserChoice*` (сломанная привязка) → `Claim`;
- `ProgId` нет вовсе → `Claim`;
- чужой `ProgId` разбирается отдельно (`decide_foreign`): команды нет или её не разобрать → `Claim`; в команде наша программа или путь похож на torrenta → `RepairStalePath`; файл из команды существует → `Keep`; файла нет → `Claim`;
- заглушка `torrent_auto_file` → `Keep`, только если за ней стоит живая чужая программа, иначе `RepairStalePath`;
- свой ProgId с нашей командой → `Keep`, с другой командой (путь старой сборки) → `RepairStalePath`.

`Keep` означает «ничего не писать»: `ensure` только читает состояние, а `repair` по определению пишет. Самоисцеление делает `heal`: сначала удаляет заведомо нерабочий слой `UserChoice*`, затем перезаписывает свои ключи. Удаляется только нерабочий выбор — пустой `ProgId` или `UserChoice*` с чужим `ProgId`, чья программа больше не существует (`broken_choice_to_delete`); живой чужой `UserChoice*` остаётся нетронутым, а свой чинится перезаписью команды в `Applications\torrenta.exe`, на которую этот `ProgId` и указывает. Поэтому `Hash` в `UserChoice` никогда не вычисляется и не подделывается.

`register(exe)` пишет только `HKCU` — права обычного пользователя:

| Ключ | Значение |
| --- | --- |
| `HKCU\Software\Classes\Torrenta.torrent` | «Торрент-файл Torrenta» |
| `...\Torrenta.torrent\DefaultIcon` | `"<exe>",0` |
| `...\Torrenta.torrent\shell\open\command` | `"<exe>" "%1"` |
| `HKCU\Software\Classes\Torrenta.magnet` | «Ссылка magnet Torrenta», тот же значок и та же команда |
| `HKCU\Software\Classes\Applications\torrenta.exe` | `Torrenta`, значок, команда, `SupportedTypes` с именованным значением `.torrent` |
| `HKCU\Software\Classes\torrent_auto_file\shell\open\command` | `"<exe>" "%1"` вместо пути старой сборки |
| `HKCU\Software\Classes\.torrent` | `Torrenta.torrent` |

Расширение прописывается явно: без этого строка остаётся привязанной к `torrent_auto_file`, а на машине без ассоциации двойной щелчок показывает диалог выбора программы вместо добавления торрента.

Три точки входа делят обязанности: `ensure(exe)` — при старте (идемпотентно, при `Keep` не пишет ничего), `status(exe)` — только чтение для `set_settings` с выключенным `associate_files`, `repair(exe)` — принудительная перерегистрация без анализа. Итог всегда упакован в `AssociationState { handler, command, is_owner, repaired, message }` и кладётся в `AssociationSlot`; `is_owner` считается как ответ оболочки (`AssocQueryStringW`/`ASSOCSTR_EXECUTABLE`) **или** совпадение команды в реестре, поэтому «мы владеем» не зависит от того, какой слой ответил. Путь сравнивается после нормализации: снимаются кавычки и вербатимный префикс `\\?\` (`\\?\UNC\` → `\\`), прямые слэши заменяются на обратные, хвостовой разделитель отбрасывается, регистр понижается.

Текст в `message` — не ошибка, а пояснение для интерфейса: «привязка сломана: в «…UserChoiceLatest» пустой ProgId, файлы .torrent не открываются» либо «файлы .torrent открывает другая программа (qBittorrent), выбрать Torrenta можно в «Параметрах Windows → Приложения по умолчанию»».

**Ограничения.**

- `UserChoice`/`UserChoiceLatest` не пишутся никогда: оболочка проверяет в них `Hash`, который умеет считать только она, поэтому подделка превратила бы файл в «не открывается» вместо «открывается не той программой». Лечение идёт через слой, который нам подконтролен.
- Живой чужой обработчик не перехватывается: `ensure` в этом случае возвращает `is_owner: false` с подсказкой, а `repair` перезаписывает только ключи Torrenta — фактическим обработчиком всё равно остаётся чужая программа, пока пользователь сам не выберет Torrenta.
- `magnet` регистрируется только как ProgId (`Torrenta.magnet`), но не как протокол: протокол `magnet:` в реестр не пишется, иначе приложение отбирало бы ссылки у торрент-клиента, который пользователь выбрал осознанно.
- Самоисцеление доказано юнит-тестами чистой `decide` (включая `qBittorrent.File.Torrent`, `uTorrent`, `Transmission.Torrent` и произвольный `SomeVendor.Product.1`), а не живым сломанным реестром: стендовый реестр при разработке пришлось чинить вручную.
- На не-Windows модуль собирается заглушками: `available: false`, `is_owner: false`, `message` = «ассоциация файлов поддерживается только в Windows».
- Ошибка реестра не ломает ни запуск, ни сохранение настроек: причина уходит в stderr (`[torrenta] привязка .torrent: …`), а состояние остаётся с `repaired: false` и текстом ошибки в `message`.

### 4.10 Портативный режим и каталог данных

1. Каталог данных выбирается один раз в `setup`, парой `DataDir { dir, portable }`; дальше его получают настройки, сессия и `AppEngine` (`app_dir()`, `portable()`), поэтому `settings.json`, `session/` и `session-data/` всегда лежат в одном месте.
2. Портативный режим включается файлом-маркером рядом с `torrenta.exe`: `torrenta-portable.txt` или `portable` (`has_portable_marker`). Маркер — обычный файл, его содержимое не читается.
3. Если маркер есть, данные складываются в подкаталог `TorrentaData` рядом с exe: каталог можно целиком скопировать на флешку, и он не смешивается с файлами самого приложения.
4. Перед переключением каталог создаётся и проверяется записью (`ensure_writable_dir`): `create_dir_all`, проверка «это каталог», пробный файл `.torrenta-write-test`. Проба нужна потому, что `create_dir_all` умеет вернуть успех, даже когда прав на запись нет: без неё первый же `save` упал бы уже во время работы.
5. Если каталог рядом с exe недоступен (нет прав, путь занят файлом), приложение не падает: причина уходит в stderr одной строкой `[torrenta] портативный режим недоступен: …`, данные остаются в каталоге конфигурации Tauri (`%APPDATA%\com.torrenta.client`), `portable` = `false`.
6. Портативность не отменяет ассоциацию: `.torrent` открывает тот бинарник, который работает сейчас (`association::current_exe`, а не `app_dir`), поэтому копия на флешке привязывается к собственному пути.
7. `portable_info` отдаёт интерфейсу `{ portable, data_dir }`: по нему окно настроек показывает, где лежат данные.

### 4.11 Проверка обновлений

1. Плагин `tauri-plugin-updater` зарегистрирован в `run`, но в `tauri.conf.json` его блок выключен: `plugins.updater = { active: false, endpoints: [], pubkey: "" }`.
2. `check_update` сравнивает `app.package_info().version` с ответом плагина и возвращает `UpdateStateDto { configured, current_version, available, message }`.
3. Пока ключа подписи нет (`updater_pubkey`/`pubkey_configured`), ответ честный: `configured: false`, `available: None`, `message` = «обновления не настроены: нет ключа подписи». Это не ошибка команды — интерфейс показывает пояснение и не предлагает обновиться.
4. Если ключ появился, но настройка неполная (нет эндпоинта, битый ключ), `configured` = `true`, а текст ошибки приходит в `message`: исключение превращается в строку, а не в отказ команды.
5. Настроенная проверка отвечает «доступно обновление {version}» или «обновлений нет». Скачивание и установка в 1.7.0 не автоматизированы: обновление по-прежнему ставит установщик.

### 4.12 Новые настройки 1.7.0

`SettingsDto` вырос до 31 поля: в 1.7.0 добавились расписание скорости, последовательная загрузка и флаг привязки файлов.

| Поле | Смысл |
| --- | --- |
| `sequential` | Новые торренты качаются последовательно; для уже добавленных решает `set_torrent_sequential` |
| `schedule_enabled` | Включает окно расписания: внутри него действуют лимиты `schedule_*`, снаружи — обычные |
| `schedule_from_min`, `schedule_to_min` | Границы окна в минутах от полуночи; окно может переходить через полночь (22:00 → 06:00) |
| `schedule_download_limit_kib`, `schedule_upload_limit_kib` | Лимиты скорости внутри окна, `0` — без лимита |
| `associate_files` | Привязывать `.torrent` при старте (по умолчанию `true`); при выключении приложение только читает состояние |

1. Нормализация: минуты приводятся по модулю 1440, лимиты ограничиваются сверху, а пустое окно (`from == to`) выключает расписание — «круглосуточного» окна не бывает.
2. Сохранение настроек не пересоздаёт движок: `set_settings` пишет `settings.json`, применяет тему, переключает автозагрузку и отправляет `EngineConfig` в живой `TorrentManager::set_config`. Прокси, расписание, лимиты, очередь и `sequential` начинают действовать сразу, перезапуска не требуют.
3. Исключение — `listen_port`: TCP-слушатель создаётся один раз в `TorrentManager::new`, поэтому новый порт применяется после перезапуска приложения.
4. Включение `associate_files` прямо в окне настроек сразу вызывает `association::ensure` и обновляет `AssociationSlot` — перезапуск не нужен, а сбой реестра не превращается в ошибку сохранения.
5. Ни портативного режима, ни проверки обновлений в `SettingsDto` нет: портативность задаётся маркером рядом с exe, обновления — конфигурацией сборки и ключом подписи.

## 5. Задачи и потоки

Приложение использует многопоточный рантайм tokio, который поднимает Tauri (`tauri::async_runtime`). Собственных потоков код не создаёт.

| Задача | Где создаётся | Что делает |
| --- | --- | --- |
| TCP-приём | `TorrentManager::new` | Слушает порт и на каждое входящее соединение запускает `handle_incoming` |
| `tracker_loop` | на каждый URL трекера (не больше шести) | Аннонсы по расписанию, обновление списка пиров |
| `drive_loop` | один на торрент | Коннектор: держит пул соединений, добирает пиры, следит за состоянием |
| `dht_loop` | один на торрент, если DHT включён | Раз в 30 с забирает пиров из кэша узла и отдаёт их коннектору; раз в 5 мин анонсирует порт отдельной задачей |
| `web_seed_loop` | один на торрент, если в метаданных есть `url-list` | По одному куску за раз догружает данные с HTTP-источников через общий `picker` и лимитер |
| `metadata_task` | только для magnet | Загрузка метаданных у пиров по BEP 9 |
| сессия пира | на каждое соединение | Две задачи: чтение сокета (пишет в канал) и основной цикл (обработка сообщений, запросы) |
| тикер состояния | `spawn_state_ticker` | Раз в 500 мс собирает снимок и отправляет `engine://state`; раз в 2 с обновляет подсказку трея и сохраняет сессию при изменении состава |
| транслятор событий | `spawn_engine_event_forwarder` | Пересылает `EngineEvent` из канала движка в `engine://event`; на `Completed` показывает уведомление Windows |
| цикл автовыключения | `spawn_auto_shutdown` | Раз в 500 мс проверяет завершение всех загрузок, ведёт отсчёт и шлёт `engine://auto-shutdown` |
| восстановление сессии | `spawn_session_restore` | Один раз после старта читает `session.json` и добавляет торренты в фоне, не задерживая показ окна |
| папка наблюдения | `watch::spawn` | Раз в 3 с просматривает `watch_dir`, добавляет новые `.torrent` и переносит обработанные в `done` |

Обмен между задачами — только через `broadcast`-каналы (`events`, `have_tx`) и `mpsc` (чтение сокета → обработчик), плюс общее состояние рантайма.

Блокирующая работа обвязки не становится отдельной задачей tokio: реестр ассоциаций и чтение `.torrent`-файла идут через `tauri::async_runtime::spawn_blocking`. Причина в том, что синхронная команда Tauri выполняется на главном потоке: ожидание реестра подвесило бы интерфейс, а `.await` внутри такой команды невозможен. Собственного пула задач в обвязке нет (см. 4.8).

## 6. Синхронизация

- **`std::sync::Mutex`/`RwLock`** — внутри движка, для коротких критических секций: карта торрентов, `Stats`, список пиров, слот узла DHT. Это осознанно: блокировки не пересекают `.await` (данные копируются и блокировка снимается до следующей точки ожидания), поэтому async-мьютексы не нужны.
- **`tokio::sync::Mutex` — только для списка проброшенных портов** (`Inner.mapping`): запрос к роутеру держит блокировку через `.await` (там сеть), а `map_port`/`unmap_port` должны идти строго по одной записи. Это единственное место, где async-мьютекс оправдан; в горячем пути таких блокировок нет.
- **Атомики** — всё, что меняется на каждом блоке: счётчики байт, скорости, число кусков, число пиров. Снимок состояния читает их без блокировок, поэтому тикер не мешает загрузке.
- **`tokio::sync::broadcast`** — события движка и уведомления о новых кусках. Отставание подписчика не смертельно: актуальные данные придут следующим тиком.
- **`tokio::sync::mpsc`** — передача разобранных сообщений от задачи чтения сокета к обработчику.

Блокирующие операции (SHA-1, чтение и запись файлов) выполняются вне критических секций: хэш считается по локальному буферу, диск трогается после снятия блокировки.

## 7. Принятые решения

| Решение | Почему так |
| --- | --- |
| Собственная реализация протокола вместо готовой библиотеки | Полный контроль над поведением (лимиты, rarest-first, состояние), отсутствие тяжёлых зависимостей, единый стиль ошибок на русском. |
| Движок — отдельный крейт, а не модуль внутри `src-tauri` | Ядро тестируется без GUI и Tauri, собирается отдельно, не тянет WebView2-зависимости. |
| Обвязка Tauri максимально тонкая | Команды только переводят вызовы; смена интерфейса или протокола не задевает друг друга. |
| Внутри движка — `std`-примитивы синхронизации, tokio — только для I/O | Меньше накладных расходов и предсказуемость: одна блокировка на короткую операцию вместо асинхронной очереди. |
| Статистика на атомиках + «отпечатки» состояния | Снимок дешёвый и не блокирующий; интерфейс не получает событий, если ничего не изменилось. |
| `storage` работает с непрерывным потоком байт | Одна логика для однофайловых и многофайловых торрентов; границы кусков могут не совпадать с границами файлов. |
| `picker` с арендой и таймаутом | Кусок не «залипает» за медленным пиром: по таймауту возвращается в пул и выдаётся другому. |
| Настройки: JSON + атомарная запись | Файл никогда не оказывается обрезанным; битый файл не мешает запуску — берутся значения по умолчанию. |
| Фронтенд без фреймворка | Малый бандл и предсказуемая отрисовка: список торрентов обновляется 2 раза в секунду, виртуальный DOM здесь не нужен. |
| Приоритеты файлов — уровни кусков в `picker`, а не отдельный планировщик | Ненужные куски просто не арендуются, а уровни лишь меняют порядок перебора: высокий приоритет опережает редкие куски, низкий работает как запасной фон. Общий кусок двух файлов получает максимум уровня, поэтому «высокий» не теряется на границе файлов. |
| Очередь и лимиты активности — в движке (`schedule`), а не в интерфейсе | Состояние `Queued` знает только ядро: слот освобождается и занимается без участия UI, лимиты действуют и для торрентов, добавленных из кода, а фронтенд остаётся тонким. |
| Файлы открываются с общим доступом на чтение, запись и удаление | Windows блокирует запуск `.exe`, пока чужой процесс держит дескриптор без `FILE_SHARE_*`; общий доступ снимает эту блокировку, а запись отпускается, как только торрент не качает. |
| Глобальный лимит — одно ведро на сессию | Иначе N торрентов получают N × лимит, и «1 МиБ/с» в настройках означает разное в зависимости от числа загрузок. Действующая скорость = минимум глобального и торрентного лимита. |
| Автовыключение через `shutdown.exe` | Не нужны WinAPI-вызовы и обработка `SeShutdownPrivilege`: системная команда сама показывает отсчёт ОС и отменяется штатным `/a`. |
| Трей — штатный `TrayIconBuilder` Tauri (фича `tray-icon`) | Значок, меню и клики живут в том же процессе и на том же событийном цикле, что и окно: не нужен ни отдельный цикл сообщений, ни WinAPI-обвязка, ни новые зависимости помимо уже подключённого Tauri. |
| Автозагрузка через `reg.exe`, а не сторонний крейт реестра | Одна запись в `HKCU` не стоит новой зависимости; `CREATE_NO_WINDOW` убирает мелькание консоли, а аргументы команд остаются чистыми функциями и тестируются без обращения к реестру. |
| Поведение окна читается из настроек в момент события | Переключатели «свёрнутым в трей» и «закрывать в трей» начинают работать сразу, без перезапуска приложения: обработчик `CloseRequested` не кэширует флаг. |
| Перепроверка — отдельная команда, а не часть добавления | Хэширование всех кусков при каждом старте задерживает загрузку; проверка по требованию быстрее и предсказуемее, а прогресс естественно виден через `pieces_have`. |
| Сессия — отдельный от настроек `session.json` с копиями `.torrent` | Настройки читаются синхронно при старте, а список торрентов меняется постоянно и нужен движку; копии метаданных отдельными файлами оставляют JSON читаемым глазами и снимают зависимость от исходного `.torrent`, который пользователь мог удалить. |
| Сессия пишется только при изменении состава (`payload_hash`) | Прогресс и скорости в файл не попадают: иначе приложение писало бы на диск каждые полсекунды, изнашивая носитель без пользы. |
| Уведомление о завершении — из Rust, а не из интерфейса | Событие `Completed` уже приходит в обвязку, поэтому уведомление работает и при скрытом окне, и при пустом списке в WebView; фронтенду не нужен доступ к плагину. |
| Подсказка трея переиспользует форматирование интерфейса | Скорости в подсказке и статусбаре совпадают до запятой в дробях; отдельный формат быстро разошёлся бы с основным. |
| Папка наблюдения переносит в `done` и успешные, и отклонённые файлы | Иначе один и тот же файл с ошибкой обрабатывался бы каждый тик и засорял журнал; перенос делает результат обработки видимым на диске. |
| Единственный экземпляр — плагин `single-instance`, зарегистрированный первым | Проверка «приложение уже запущено» должна произойти до создания окон и остальных плагинов, иначе второй процесс успеет поднять WebView2 и потратит память впустую. Плагин передаёт `argv` второго запуска в колбэк первого, а второй процесс завершается сам. |
| Источник из `argv` — чистая функция `source_from_args`, а не разбор в колбэке | Правила «magnet или `.torrent`, без учёта регистра, флаги игнорируем» покрыты юнит-тестами без запуска приложения и графической сессии; колбэк плагина остаётся в три строки. |
| Очередь `PendingOpen` с take-once вместо буфера событий | Окно создаётся скрытым и грузит интерфейс после `setup`, поэтому сигнал может обогнать подписку. Один слот с забором ровно один раз проще и надёжнее, чем хранение истории событий, и исключает двойное открытие диалога. |
| Единственный экземпляр и открытие `.torrent` — одна задача, а не две | Windows запускает новую копию `.exe` на каждый двойной щелчок по ассоциированному файлу: без перехвата второго запуска ассоциация открывала бы второй клиент с тем же портом и каталогом. Вместе они дают поведение «файл открылся в том же окне». |
| DHT, PEX и web seeds — отдельные модули без сети внутри | `dht` держит свой UDP-сокет, `pex` только упаковывает и разбирает адреса, `web_seed` отвечает за один HTTP-источник. Каналы, пикеры и таймеры остаются в `engine`, поэтому модули тестируются без сети, а один и тот же `pex` годится и для входящих, и для исходящих пакетов. |
| Web seed качает по одному куску за раз | Параллельные запросы к HTTP-источникам делят пропускную способность с пирами и легко обгоняют их по объёму. Один кусок за раз проходит через тот же `picker` и тот же лимитер, поэтому догрузка не ломает ни выбор файлов, ни лимиты скорости. |
| UDP не ходит через прокси | SOCKS5 `UDP ASSOCIATE` не реализован, а HTTP CONNECT UDP не проксирует вовсе. Честнее оставить DHT и UDP-трекеры прямыми, чем показывать в настройках неработающий туннель. |
| Проброс порта — best effort и без интерфейса | UPnP-IGD и NAT-PMP поддерживаются роутерами непредсказуемо, а ошибка проброса не должна мешать загрузке. Поэтому результат нигде не показывается: включённая настройка значит «попробовать», а не «порт точно открыт». |
| Лимиты раздачи живут в тикере, а не в отдельном таймере | Ratio и время раздачи проверяются там же, где считается статистика (500 мс): отдельный таймер дублировал бы счётчики и расходился бы с ними. Сработавший лимит только поднимает `seed_limit_reached` — решение продолжить остаётся за пользователем. |
| `proxy.rs` и `port_map.rs` — на голом tokio, без сторонних крейтов | SOCKS5, HTTP CONNECT, `base64`, SSDP-поиск и NAT-PMP — сотни строк простого протокола; своя реализация не тянет зависимостей, проверяется на локальном фейковом сервере и не поднимает MSRV крейта. |
| Привязка `.torrent` — забота приложения, а не только установщика | Установщик выполняется один раз и не видит пользовательский выбор: после обновления в реестре остаётся ProgId, указывающий на старую сборку. Приложение проверяет привязку на каждом старте и чинит путь само, поэтому переезд каталога или портативная копия не «ломают» двойной щелчок. |
| Решение об ассоциации принимает чистая `decide`, а реестр — только адаптер | Правила «когда лечить, а когда не лезть» покрыты юнит-тестами без Windows и графической сессии; изменение политики не требует трогать код чтения и записи реестра. |
| Портативный режим — файл-маркер рядом с exe, а не флаг сборки | Копию каталога можно целиком унести на флешку и запустить без установки; флаг сборки требовал бы отдельного артефакта и не позволял бы иметь обычную и портативную копию из одной сборки. |
| `check_update` без ключа подписи отвечает `configured: false` | Честный ответ лучше, чем «обновлений нет»: иначе интерфейс обещал бы проверку, которой нет, и пользователь считал бы, что версия актуальна. |

## 8. Следствия и ограничения архитектуры

- **Диск и хэш блокируют задачу tokio**: `storage` использует `std::fs`, отдельного пула блокирующих задач нет. Для локальных файлов это приемлемо (кусок — сотни килобайт, операции короткие), но при медленном сетевом диске возможны задержки других задач рантайма.
- **DHT — один раунд `get_peers` на анонс**: узел ищет пиров по конкретному info-hash и кэширует ответы, но не обходит таблицу рекурсивно и не обрабатывает `port`-сообщения от пиров; таблица пополняется bootstrap-адресами, узлами из ответов и теми, кто сам прислал запрос, а компактные адреса пиров разбираются только как IPv4. Если UDP в сети закрыт, узел остаётся пустым и discovery возвращается к трекерам — ошибки это не вызывает.
- **PEX — только IPv4 и без тестов на исходящий таймер**: формат BEP 11 задаёт 6 байт на адрес, поэтому IPv6-пиры через PEX не передаются, а `dropped` мы не учитываем. Интервал 60 с проверяется в живом обмене: автотестами покрыты сборка, разбор и дифф пакетов, но не расписание отправки.
- **Web seeds — только выключатель и константы**: списка URL и приоритетов источников в интерфейсе нет, таймауты (10 с на соединение, 30 с на чтение) и число параллельных запросов (`max_parallel: 4`, движок берёт по одному куску) заданы в модуле, а не в настройках. Прокси для web seeds — та же строка, что и для трекеров, поэтому «прокси для HTTP» отдельно не настраивается.
- **Прокси — только TCP, без `socks5h`-разрешения имён**: имена резолвит система, поэтому `socks5h` ведёт себя как `socks5`, а `https://`-прокси открывается как `http`-туннель (TLS до прокси не поднимается). UDP-трафик (DHT, UDP-трекеры) идёт мимо прокси, HTTP-прокси поддерживает только `Basic`.
- **Проброс порта — TCP, без продления и без выбора внешнего порта**: пробрасывается только `listen_port`, UDP-порт DHT не пробрасывается; запрос требует совпадения внешнего и внутреннего порта (альтернативный не предлагаем), а аренда в 3600 с обновляется лишь при старте и смене настроек — после истечения порт на роутере закрывается до перезапуска. Шлюз для NAT-PMP определяется эвристикой `x.y.z.1`, реальная сеть проверяется только `#[ignore]`-тестом.
- **Лимиты раздачи требуют ручного продолжения**: проверка идёт каждые 500 мс, время раздачи не течёт на паузе и в очереди, а сработавший лимит только поднимает `seed_limit_reached` и останавливает раздачу — автовозобновления нет, паузу снимает пользователь.
- **uTP не реализован**: обмен идёт только по TCP, поэтому пиры, достижимые лишь через uTP (например, за симметричным NAT), не подключаются. DHT и PEX помогают только там, где TCP достижим, и заменой uTP не являются.
- **Предпросмотр magnet по-прежнему без DHT**: `preview_magnet` работает через трекеры из ссылки (до пяти), а magnet без `tr` отклоняется с понятной ошибкой — узел DHT поднимается только вместе с добавленным торрентом.
- **Выборочная загрузка — «всё или ничего» по файлу**: гранулярность ограничена файлами торрента; кусок, общий для выбранного и снятого файла, скачивается целиком, так что реальный объём может быть чуть больше суммы выбранных файлов. По той же причине общий кусок получает максимальный из приоритетов файлов.
- **Очередь без ротации по времени**: лимиты «одновременно скачивать/раздавать» соблюдаются по порядку добавления; пока активный торрент не завершится, не встанет на паузу или не будет удалён, слот не переходит следующему. Ограничение осознанное — простое и предсказуемое поведение вместо таймеров и квот.
- **Перепроверка без переподключения пиров**: `verify_all` останавливает обмен и хэширует диск, но не перезапускает трекеры и не сбрасывает пул соединений; после проверки обмен продолжается с уже известными пирами.
- **Запись отпускается, пока торрент не качает**: на паузе, в очереди и во время проверки файлы открыты только на чтение, поэтому внешняя запись в них вернёт ошибку. Это цена того, что скачанный `.exe` можно запустить, не закрывая клиент.
- **Сессия хранит параметры, но не прогресс**: `session.json` переживает перезапуск, а прогресс восстанавливается по данным на диске; magnet-торренты после перезапуска качают метаданные заново, поэтому до их получения имя и размер неизвестны, а приоритеты `Low`/`High` теряются. Испорченная запись пропускается, остальные восстанавливаются.
- **Папка наблюдения — только верхний уровень**: подкаталоги не обходятся, а файл, который не удалось добавить, всё равно переносится в `done`, поэтому причина ошибки остаётся только в журнале.
- **Уведомления целиком зависят от Windows**: оформление, звук и разрешение на показ задаёт система; при выключенных системных уведомлениях приложение не узнаёт об этом и просто логирует ошибку.
- **Трей и автозагрузка — только Windows**: значок использует системную область уведомлений, а автозагрузка — ветку `HKCU\...\Run`; вне Windows `autostart` — заглушка, а значок создаётся средствами Tauri и может вести себя иначе. Автозапуск общий для всех пользователей машины не поддерживается.
- **Трей без «живой» проверки в тестах**: создание значка, клик по нему и скрытие окна по крестику требуют графической сессии, поэтому покрыты только логикой и ручным прогоном; юнит-тестами проверяются константы трея, сборка текста подсказки и аргументы реестра.
- **Ассоциация `.torrent` — объявление в бандлере плюс проверка в приложении**: `tauri.conf.json` лишь объявляет `fileAssociations`, запись установщика живёт в `HKCU\Software\Classes` (WiX — рекламируемыми ключами), а проверяется она только на установленной системе. С 1.7.0 источник истины — реестр, прочитанный при старте: приложение дописывает свои ключи и чинит путь после обновления (см. 4.9). Описание ProgID в манифесте записано латиницей: WiX собирает `main.wxs` с кодовой страницей 1252, и кириллица в `ProgId/@Description` ломает MSI-сборку (`LGHT0311`); в реестре описание русское.
- **Выбор пользователя в `UserChoice`/`UserChoiceLatest` приложению не подчиняется**: оболочка проверяет там `Hash`, который умеет считать только она, поэтому записать свой ProgId поверх чужого нельзя, а подделка привела бы к «файл не открывается». Отсюда правило: живой чужой обработчик остаётся, а сменить его пользователь может только в «Параметрах Windows → Приложения по умолчанию».
- **Узкая гонка `PendingOpen` при старте**: если второй экземпляр передаст источник в первые десятки миллисекунд, пока `setup` ещё не выполнил `app.manage(PendingOpen)`, окно первого экземпляра поднимется, событие уйдёт, но сам источник не сохранится — пользователь увидит обычное окно и добавит файл вручную. Практически недостижимо (второй запуск требует действия пользователя), поэтому состояние инициализируется сразу после `AppEngine`.
